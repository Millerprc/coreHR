# 第二阶段录用衔接交付回执

> 日期：2026-08-09
>
> 范围：主管理员确认录用后，衔接候选人、人员档案、待入职劳动关系和主任职
>
> 状态：`IMPLEMENTED_AND_VERIFIED`

## 1. 已交付

- 应聘记录到达 Offer 阶段后，主管理员通过独立的“确认录用”操作生成待入职结果。
- 新人员自动创建 Person、分配并占用六位工号；再次入职可选择已有 Person 并沿用原工号。
- 自动创建 `pending_start` 劳动关系，计划入职日期、员工类型和四类法人主体进入正式字段。
- 自动使用招聘需求的组织和职务创建主任职，不要求招聘需求存在空编，也不以招聘人数阻断录用。
- 候选人同步转为 `converted` 并关联 Person；应聘记录同步转为 `hired`。
- 管理端支持四类主体默认一致，也允许分别选择薪资、社保和个税主体。

## 2. 一致性与并发规则

- 普通应聘状态接口不能直接把记录改为 `hired`，防止出现“已录用但没有待入职档案”的半成品。
- 新表 `application_hire_conversions` 保存应聘、候选人、Person、Employment、Assignment 的唯一转换链路。
- 每次确认录用必须提供 UUID 幂等键；同一内容重试返回同一转换记录，不重复分配工号或创建劳动关系。
- 同一幂等键用于不同内容时返回冲突；同一应聘记录不能被转换两次。
- 转换在一个数据库事务中完成，任何一步失败都会整体回滚。
- 同一自然人的劳动关系有效期冲突继续由 Employment 领域规则统一拦截。

## 3. 审计证据

- Person、Employment、Assignment 各自保留创建审计。
- 应聘记录的录用、候选人的转换和转换链路均保存操作人、原因、Trace ID 和前后状态。
- 转换记录保存计划入职日期、员工类型、操作人和操作时间。

## 4. 明确边界

- 本能力负责 Offer 接受后的结果衔接，不替代第二阶段入职审批流程；未来生效的人事事件仍由人事事件引擎处理。
- 招聘需求人数和编制只展示，不作为录用强卡控条件。
- 员工类型代码当前由主管理员填写；正式枚举和中文名称待企业编码对照表导入。
- 候选人的手机号、邮箱仍保存在招聘记录中；人员档案正式联系方式字段待字段验收表确认后再映射。
- 本次测试仅使用本机 Docker 和合成数据，未写入或上传企业真实数据。
