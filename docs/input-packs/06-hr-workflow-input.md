# 企业输入包06：人事流程图与审批规则

> 状态：`ONBOARDING_IN_PROGRESS / INITIATOR_CONFIRMED`
> 输入顺序：第3项
> 数据安全：只填写角色、条件字段和流程规则；不要填写真实员工姓名、账号、申请记录或审批意见

## 1. 本轮目标

把入职、转正、调动、兼岗、借调、离职、撤回/更正和回退等企业流程图，转换为可发布、可测试、可追溯的流程定义与人事事件衔接规则。

需求编号、领域边界和完成定义以[第二阶段需求规格](../01-foundation/12-第二阶段需求规格.md)为准；页面和业务UAT以[第二阶段PRD](../01-foundation/13-第二阶段PRD.md)为准。

可以直接提供现有流程图；如果流程图不便导出，则填写以下模板：

1. [流程清单](./templates/04-hr-processes.csv)
2. [流程节点](./templates/04-hr-workflow-nodes.csv)
3. [节点办理人](./templates/04-hr-workflow-assignees.csv)
4. [流程连线与条件](./templates/04-hr-workflow-routes.csv)

## 2. 建议提供顺序

一次只确认一个流程，推荐顺序：

1. `ONBOARDING` 入职。
2. `CONFIRMATION` 转正。
3. `TRANSFER` 调岗。
4. `CONCURRENT_ASSIGNMENT` 兼岗。
5. `SECONDMENT` 借调。
6. `TERMINATION` 离职。
7. `WITHDRAWAL` 撤回入职、`EMPLOYMENT_CORRECTION` 更正。
8. 各流程的回退规则。

每个流程完成映射、合成数据测试和业务Review后，再处理下一个，不要求一次交齐全部流程。

## 3. 当前引擎已经具备

- 流程定义、草稿版本、发布版本和运行实例。
- `start/approval/action/end`四类节点。
- 审批节点会签`all`和或签`any`。
- 多个用户、角色或表达式形式的办理人引用。
- 结构化条件组，支持`all/any`及相等、不等、大小、包含和存在性判断。
- 条件分支最多命中一条；无命中时走唯一默认线；歧义时失败关闭。
- 审批通过后，今天生效的人事事件立即执行，未来事件等待生效日。
- 驳回不改变业务结果；回退形成新事件并保留原记录。

## 4. 企业适配前仍缺的能力

以下内容不能从流程图之外猜测，收到输入后需要继续开发或配置：

| 缺口 | 为什么需要输入 |
|---|---|
| 动态办理人解析 | 需要明确“申请人主管、目标组织负责人、HRBP、SSC、法人负责人”等各自从哪条关系取值 |
| 任务办理权限 | 当前第一批主管理员可以处理任务；开放其他角色前，必须校验实际登录人属于任务办理人或授权代理人 |
| 超时、催办和升级 | 需要每个节点的SLA、提醒频率、升级对象及节假日口径 |
| 撤回、重新提交、转办、加签、减签 | 需要流程级允许条件和已完成节点如何保留 |
| 并行分支 | 当前会签是同一审批节点内多人处理，不等同于两条业务支线并行后汇合 |
| 动作节点插件 | 当前动作节点自动向后推进；若需写外部OA、企业微信或其他系统，必须定义动作契约和失败重试 |
| 数据范围与字段权限 | 审批人能看到哪些人员字段、附件和变更前后值必须单独确认 |

## 5. 模板填写规则

### 5.1 流程清单

- `workflow_code`使用稳定大写英文代码，发布后不随中文名变化。
- `event_type`必须对应人事事件，如`TRANSFER`；一个流程可以只服务一种事件。
- `default_execution_mode`为`direct`或`approval`。正式企业流程通常填`approval`。
- `effective_date_source`说明生效日期来自申请人、HR确认、固定规则还是审批完成日。
- `rollback_mode`填`direct/approval/by_scenario`。

### 5.2 节点

- 每个流程恰好一个`start`和一个`end`。
- `approval`必须填写`sign_mode=all/any`。
- `action`仅表示无需人工决策的业务动作，不用于执行任意脚本。
- 当前流程版本不允许环路；驳回重提应创建新提交/新实例，而不是连线回到前节点。

### 5.3 办理人

- `assignee_type=user`只适合固定系统账号，不填写自然人姓名。
- `assignee_type=role`填写稳定角色代码。
- `assignee_type=expression`填写受控解析器代码，例如`INITIATOR_MANAGER`；不是Python、SQL或自然语言表达式。
- `fallback_role`必须明确动态关系缺失时由谁兜底；禁止默认放行或跳过审批。

### 5.4 条件连线

- 一个`route_code`可用多行表达多条条件规则。
- `condition_mode=all/any`表示多条规则全部满足或任一满足。
- `condition_path`必须来自该业务对象的白名单字段，不接受SQL、脚本或函数。
- 分支节点必须有且只有一条默认线；多条条件同时命中时系统拒绝推进。

## 6. 每个流程需要回答的业务问题

1. 谁可以发起？是否允许代发起？
2. 哪些状态下可以发起？与进行中的同类流程是否互斥？
3. 生效日期由谁填写，能否修改，审批完成日晚于生效日时如何处理？
4. 每个节点是会签还是或签，办理人如何解析？
5. 分支条件、比较值及默认路径是什么？
6. 驳回到结束还是退回修改？是否允许重新提交？
7. 审批中能否撤回；已审批但未生效能否取消？
8. 超时、催办、升级、转办、加签和减签规则是什么？
9. 通过后具体改变哪些字段或关系？失败能否重试？
10. 回退采用直接、审批还是按场景；下游已同步时如何再次同步？

### 6.1 入职流程已确认规则

以下规则已于2026-08-12确认：

- `ONBOARDING`表示待入职劳动关系转为在职，不包含Offer确认、人员建档或待入职劳动关系创建。
- SSC可以发起入职流程。
- 系统管理员可以代发起或补录；必须填写原因并记录审计日志。
- HRBP、招聘人员、业务主管和员工本人本期不能发起，后续开放时再补角色和数据范围规则。

当前实现已增加三项不依赖审批图的保护：只有`pending_start`劳动关系可以创建或执行入职事件；同一劳动关系不能并行存在多个待审批、待生效、已排期或失败待重试的入职事件；`SSC_ADMIN`角色拥有独立的`ONBOARDING_INITIATE`权限，主管理员通过通配权限代发起，原因去除首尾空白后不能为空并进入审计日志。主管理员已经可以在“账号与权限”工作区创建SSC账号、分配角色和启停访问；SSC专用入职操作界面、正式审批链和动态办理人仍属于待实现项，不能据此宣称入职流程已经交付。

## 7. 验收交付物

每个流程完成后必须同时提供：

- 可读流程图和版本化流程定义。
- 节点、办理人解析和条件白名单。
- 人事事件输入/输出字段及生效规则。
- 通过、驳回、撤回、未来生效、执行失败、重试和回退测试。
- 流程实例、任务、选路历史、人事事件和审计记录的对账说明。

流程图未提供时，现有通用引擎可以继续演示，但不能宣称企业审批链完成。
