# 企业输入包05：人员档案字段验收

> 状态：`ACCEPTED / READY_FOR_IMPLEMENTATION`
> 确认日期：2026-08-12
> 输入顺序：第2项；首个职务体系样本已确认
> 数据安全：只确认字段定义和规则，不在本文或模板中填写真实姓名、工号、证件、电话、地址、银行或合同内容

## 1. 本轮目标

把旧 EHR 字段和 coreHR 领域模型之间的边界冻结为可开发、可迁移、可验收的人员档案合同，避免把旧表整行复制或把未确认字段塞进 JSON。

本输入包覆盖：

1. 自然人基础身份。
2. 证件、联系方式、地址和紧急联系人。
3. 每次雇佣、四类法人主体、主任职及其他关系。
4. 汇报、协议和人员标签。
5. 教育、工作、家庭、附件及银行资料的阶段边界。

字段矩阵见[人员字段验收模板](./templates/03-personnel-field-acceptance.csv)。2026-08-12用户确认全部采用推荐值；模板中的`business_decision=ACCEPT_RECOMMENDED`构成本轮Accepted字段合同。

## 2. 已由现有规则确定，不再重复询问

- Person 是永久自然人；二次入职新增 Employment，但复用 Person 和原六位工号。
- 同一自然人在同一有效期间最多一条集团内法人劳动关系；合作、派遣等协议关系可以并存。
- 待入职只要明确计划入职日期即可建档并占用工号。
- 主组织、主职务同一日期唯一；兼岗、借调、项目和虚拟组织可以并存。
- 合同、发薪、社保和个税主体分别保存，同一日期默认一致但允许分别调整。
- 基础档案允许主管理员直接更正并审计；雇佣、组织、职务和主体变更由人事事件维护。
- 员工自助、移动端和 MCP 修改档案不属于当前第一批主管理员范围。
- 旧 EHR 的 `nationality_id/nationality` 实际表示民族，不能写入国籍；`country` 需要转换为 ISO 国家或地区代码。

## 3. 推荐字段模型

### 3.1 自然人

| 字段 | 推荐规则 |
|---|---|
| 法定姓名 `legal_name` | 建立 Person 必填；不把昵称当法定姓名 |
| 展示姓名 `display_name` | 必填；默认等于法定姓名，允许按审计更正 |
| 曾用名 `former_name` | 可选；第一版保留一个文本字段，历史变化进入审计 |
| 性别 `gender_code` | 可选字典；不阻止建档 |
| 出生日期 `birth_date` | Person 可空；转为在职前建议补齐，不作为全类型强必填 |
| 国籍 `nationality_code` | ISO 国家代码，可空；与民族分开 |
| 所在国家/地区 `country_code` | ISO 国家或地区代码，可空；与国籍分开 |
| 民族 `ethnicity_code` | 普通字典，可空；仅适用于有该概念的国家/地区 |
| 婚姻、政治面貌 | 可选普通字典；不进入首批必填项 |

不强制拆分姓、名、中间名。第五阶段多国家与多语言启用前，以法定全名和展示全名为主，避免中国姓名规则污染其他国家。

### 3.2 证件

- 一名 Person 可以有多张证件，但同一时点最多一张主要证件。
- 创建待入职或在职劳动关系前必须有一张已确认的主要证件；外部合作人员可以先建 Person，证件暂缺时进入数据质量清单。
- 唯一性使用“证件类型 + 签发国家/地区 + 规范化号码”的不可逆检索摘要，不在普通索引、日志或错误中保存明文。
- 证件号码加密保存，页面默认脱敏；明文查看、导出和打印必须独立授权并记录访问审计。
- 附件引用在对象存储、病毒扫描和访问权限落地后启用，不把二进制文件放入 PostgreSQL 普通业务表。

### 3.3 联系方式、地址和紧急联系人

- 个人手机、工作手机、个人邮箱、工作邮箱均为一对多联系方式；支持主要标记和有效期。
- 个人手机和个人邮箱属于敏感个人信息；工作联系方式属于内部人员信息。
- 地址拆分国家/地区、行政区和受保护的详细地址，不用一个公开 JSON 保存完整地址。
- 紧急联系人独立建模，姓名、关系和联系方式均受人员档案权限控制。
- 第一批主管理员档案允许这些信息为空；正式入职流程的必填时点由后续流程图确认。

### 3.4 雇佣与关系

| 范围 | 维护方式 |
|---|---|
| 员工类型、状态、计划/实际入职、转正、离职 | Employment；状态和日期变化走人事事件 |
| 合同、发薪、社保、个税主体 | Employment 的有效日期主体关系；同类同日唯一 |
| 主组织、主职务、兼岗、借调、项目、虚拟组织 | EmploymentAssignment；按有效日期保存 |
| 实线、虚线汇报 | ReportingRelation；独立于组织负责人 |
| 合作、派遣等非劳动关系 | AgreementRelationship；可以与 Employment 并存 |
| BP 和负责人 | 使用现有组织关系模型，不复制到 Person 扩展字段 |

## 4. 敏感级别默认值

| 级别 | 示例 | 默认保护 |
|---|---|---|
| `INTERNAL` | 展示姓名、工号、工作邮箱、组织职务 | 登录和数据范围控制；禁止公开暴露 |
| `SENSITIVE` | 出生日期、个人电话、个人邮箱、地址、家庭和紧急联系人 | 默认脱敏；字段权限；导出控制；访问审计 |
| `HIGH` | 证件号码、银行账户、证件附件 | 加密；不可逆检索摘要；独立明文权限；逐次访问审计 |

银行账户属于第四阶段发薪边界。第一阶段只保留未来实体位置，不接收真实银行数据。

## 5. 与当前系统的差距

当前代码已经具备 Person、Employment、EmploymentAssignment、AgreementRelationship、六位工号、人员档案聚合页面、审计和劳动关系重叠校验。

仍需在字段确认后开发：

1. 法定姓名、民族、婚姻等基础字段补齐。
2. 证件、联系方式、地址、紧急联系人等归一化子实体。
3. 敏感值加密、规范化摘要、默认脱敏、字段权限和明文访问审计。
4. 人员首版本、雇佣、任职和关系的分批迁移任务及拒绝清单。
5. 人员搜索和受控导出。

在第3项完成前，不把旧 EHR 的证件、电话、邮箱、详细地址和其他真实敏感值灌入 coreHR。

## 6. 已确认的第一组问题

以下8项已于2026-08-12全部按推荐值确认；后续如需改变，必须形成新的字段合同版本和迁移影响评审。

1. 法定姓名必填，展示姓名默认等于法定姓名：是否接受？
2. 不强制拆分姓/名，只保存法定全名、展示全名和曾用名：是否接受？
3. 出生日期、性别、国籍允许建档时为空，但劳动关系转为在职前进入数据质量检查；缺失先告警、不阻断：是否接受？
4. 民族、国籍、所在国家/地区三个字段独立：是否接受？
5. 待入职或在职劳动关系生效前必须有主要证件；外部合作人员可以暂缺：是否接受？
6. 证件号码采用“加密值 + 脱敏值 + 不可逆检索摘要”，不允许普通明文列：是否接受？
7. 联系方式、地址和紧急联系人第一批允许为空，正式流程必填时点等流程图确认：是否接受？
8. 教育、工作经历、家庭成员第一阶段建模但非必填；附件等待安全存储；银行账户延后第四阶段：是否接受？
