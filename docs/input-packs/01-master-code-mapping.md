# 企业输入包 01：主数据与稳定编码对照

> 状态：`WAITING_FOR_BUSINESS_CONFIRMATION`
> 适用阶段：第一阶段正式初始化，并为第二、第三阶段历史数据映射提供基础
> 数据安全：只填写代码、名称、有效日期和业务规则，不填写人员姓名、证件、电话、薪酬或其他个人数据

2026-08-11 已执行本机非敏感枚举查询；当前 `ehr_source` 仅含每表首行，详细证据和候选映射见[非敏感枚举提取结果](./01-enum-extraction-result.md)。以下首行样例已经预填，但完整枚举仍需从完整旧系统数据库单独导出。

## 1. 这次只解决什么

本输入包只冻结“同一个业务对象以后用什么稳定代码识别”。完成后可以继续开发：

1. 第一阶段正式初始化导入、校验、拒绝报告和重复执行能力。
2. EHR 历史 ID/名称到 coreHR 主数据的确定性映射。
3. 人员、任职、编制、流程和考勤数据导入时的外键校验。

本轮不要求提供真实人员行、审批流程图、合同细节或考勤公式。

## 2. 已确认编码规则

组织类型等系统稳定配置项已确认采用以下规则。具体组织实例的新编码仍使用纯数字流水号，初始化导入时保留历史组织编码。

| 项目 | 推荐规则 |
|---|---|
| 稳定代码 | 英文大写、数字、下划线；创建后不因中文名称变化而修改 |
| 中文名称 | 作为显示名称，可按有效日期版本化 |
| 国家/地区 | ISO 3166-1 两位或三位大写代码 |
| 币种 | ISO 4217 三位大写代码 |
| 历史来源键 | 保留 `source_system + source_table + source_id`，不把名称当唯一键 |
| 生效日期 | `YYYY-MM-DD`；未知历史起点统一进入迁移问题，不猜日期 |
| 停用 | 保留原代码并标记失效日期，不复用给其他业务对象 |
| 未知值 | 使用“待确认/拒绝导入”，不使用 `OTHER` 静默吞并，除非业务明确批准 |

## 5. 表 C：历史组织编码

组织结构来源包括 `ehr_department_snap` 和员工部门字段。初始化历史树时至少需要以下字段：

| 来源部门ID | 历史组织编码 | 组织名称 | 父来源部门ID | 父历史编码 | coreHR组织类型代码 | 国家代码 | 生效日期 | 失效日期 | 状态 |
|---|---|---|---|---|---|---|---|---|---|
| 待填 | 可空 | 待填 | 根节点可空 | 可空 | `GROUP/BG/BU/DEPARTMENT` | 可空 | 待填 | 可空 | `active/inactive` |

规则：

- 历史组织编码存在时原样保留；缺失时由 coreHR 生成新代码。
- 同一生效期间只能挂在一个上级之下。
- 只靠父组织名称无法唯一确定上级时，该行进入拒绝报告。

## 7. 表 E：劳动关系状态

来源字段为 `ehr_employee_info.employee_status_id`。coreHR 当前执行器使用以下状态：

| coreHR状态 | 含义 | 进入方式 |
|---|---|---|
| `pending_start` | 待入职 | 创建待入职劳动关系 |
| `active` | 有效劳动关系 | 入职或转正事件结果 |
| `terminated` | 已离职 | 离职事件结果 |
| `withdrawn` | 已撤回入职 | 撤回事件结果 |

请填写来源映射：

| 来源状态ID | 来源状态名称 | coreHR状态 | 是否保留为历史标签 | 备注 |
|---|---|---|---|---|
| `1` | 在职 | `active`（建议） | `false`（建议） | 首行样例已识别，待确认 |
| 待填 | 其他实际状态 | 四个状态之一或“待新增业务维度” | `true/false` | 待填 |

如果旧系统存在“试用期、停薪留职、退休返聘”等状态，请不要直接塞进上述四项；先标记为“待新增业务维度”，判断它属于劳动关系状态、员工类型还是人员标签。

## 12. 最小提交方式

不需要一次填完所有历史行。按以下顺序提交即可：

1. 第 2 节编码规则和表 A 的四个组织类型已经确认；补充旧系统对应值。
2. 再提供表 D、E、F、H 的所有枚举值；这些通常行数较少。
3. 再提供表 B 法人清单。
4. 最后提供表 C 组织和表 G 职务的大批量对照文件。
5. 表 I 可以与兼岗/借调流程图一起确认。

可以直接修改本文件，也可以提供 Excel/CSV/SQL。若提供 Excel，建议每个表单独一个工作表，并保留本文件中的列名。

如授权由Codex在本机自动提取第1至2步的小枚举，只运行[非敏感枚举只读提取SQL](./sql/01-export-non-sensitive-enums.sql)。该查询已经限定输出字段，不读取人员标识、姓名、证件、联系方式、地址、薪酬或银行信息，也不包含任何写操作。执行结果仅保存在当前本机工作区，用于生成候选对照表，仍需业务确认后才能进入正式导入。

## 13. 完成闸门

以下条件全部满足后，输入包 01 才标记完成：

- 每个来源枚举值恰好对应一个目标代码，或明确进入拒绝清单。
- 法人、组织和职务都有不依赖显示名称的稳定业务键。
- 目标代码没有重复、没有被复用于不同语义。
- 组织父级和类型可确定，不能确定的行有明确问题编号。
- 员工类型占编规则带有效日期。
- 文档和样例中不含真实人员敏感数据。
