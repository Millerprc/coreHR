## 1. 本轮目标

把“8GB服务器运行MVP、成功后迁移32GB服务器、未来万人场景”转换为可执行的环境清单、恢复目标和压测验收标准。建议填写：

1. [部署环境清单](./templates/07-deployment-inventory.csv)
2. [容量场景](./templates/07-capacity-scenarios.csv)
3. [备份恢复目标](./templates/07-backup-recovery-objectives.csv)

## 2. 当前边界

- 当前Docker Compose适合本机开发和业务验收，不等于生产部署方案。
- 8GB单机可作为第一阶段MVP/UAT候选，但必须实际测量资源占用，不能据此承诺万人容量。
- 32GB迁移时可按瓶颈拆分Web、API、Redis和PostgreSQL；是否拆机以监控和压测证据决定。
- MySQL、Oracle、多租户及Apusic等应用服务器中间件继续保留到第五阶段评估，前三阶段不为兼容性提前增加复杂度。
- “一万人同时在线”不等于“一万个请求同时到达”。必须分别给出集中时间、请求次数、响应目标和数据规模。

## 3. 推荐部署基线

### 3.1 MVP/UAT（8GB候选）

- 单机Docker Compose，固定镜像版本，数据库使用持久卷。
- 仅通过受控入口暴露Web；数据库和Redis不对外网开放。
- TLS终止、独立强凭证、最小权限、资源上限和日志轮转必须配置。
- 利用现有`/health/live`和`/health/ready`做存活与就绪检查。
- 上线前执行数据库备份，变更失败按运行手册回退应用；数据库迁移必须先证明可前向兼容或有恢复方案。

### 3.2 后续正式环境（32GB及以上）

- 默认采用滚动发布；数据库变更使用“先扩展、后迁移、再收缩”，保持新旧应用短期兼容。
- 只有具备双倍基础设施和明确切换/回切方案时才采用蓝绿发布。
- 高流量变更可在具备真实监控后做小流量发布；当前不引入Kubernetes作为前置条件。
- 当单机数据库、缓存或API成为明确瓶颈时再拆分，不凭主观判断加中间层。

## 4. 安全与可运维验收

- TLS、密钥外置、凭证轮换、最小权限、依赖与镜像漏洞检查。
- 非root容器、禁止额外权限、CPU/内存限制、磁盘容量和日志轮转告警。
- API限流、请求大小限制、超时及关联ID；日志禁止记录密码、令牌和人员敏感字段。
- 数据库、附件/文档、配置和审计数据分别定义备份；备份必须加密、隔离并限制访问。
- 不只检查“备份成功”，还要定期在隔离环境执行恢复演练并记录耗时与校验结果。
- 监控至少覆盖可用性、响应时间、错误率、CPU、内存、磁盘、数据库连接/慢查询和队列积压。

## 5. 容量模型填写规则

- `active_users`是场景内活跃用户，不代表同时请求数。
- `ramp_seconds`说明用户进入场景的集中程度；它直接决定峰值请求率。
- `target_rps`没有业务证据时留空，由场景计算和首轮压测校准。
- 每个场景同时给出P95/P99、错误率、数据集大小和冷/热缓存状态。
- 打卡写入、考勤查询和薪酬查询必须分开测；薪酬属于第四阶段，不纳入前三阶段通过条件。
- 示例“10000人在60秒各打一张卡”约为167 RPS，只是建模样例，不是已确认目标。

## 6. 备份与恢复填写规则

- `RPO`表示最多可接受丢失多少时间的数据；`RTO`表示故障后多久恢复服务。
- PostgreSQL、附件、配置、审计和日志分别填写，不能用一个口号代替。
- MVP示例值仅帮助讨论，不自动成为正式承诺；生产值必须由业务和运维共同确认。
- 任何跨服务器迁移先完成备份、恢复验证和回退演练，再切换入口。

## 7. 本轮完成条件

1. 环境清单给出CPU、内存、磁盘、操作系统、网络入口和备份去向。
2. 三类核心场景写清用户数、集中时间、请求次数和响应目标。
3. 每类数据确认RPO、RTO、保留期、加密和恢复频率。
4. 在8GB机器完成基线测试并形成报告后，才能决定是否迁移或拆分组件。
5. 万人场景必须以可重复压测报告、监控证据和容量余量验收，不能只看页面能否打开。
