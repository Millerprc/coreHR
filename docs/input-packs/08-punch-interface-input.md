# 企业输入包08：打卡来源与接口契约

> 状态：`TEMPLATE_READY / WAITING_FOR_SOURCE_CONTRACT`
> 输入顺序：第6项
> 数据安全：只填写字段定义和合成示例；不要填写真实员工、设备、位置、令牌、密码或完整供应商报文

## 1. 本轮目标

把企业微信、考勤设备或其他平台的打卡数据转换为统一、可补传、可审计的原始打卡证据。建议填写：

1. [打卡来源清单](./templates/06-punch-sources.csv)
2. [来源字段映射](./templates/06-punch-contract-fields.csv)
3. [补传、冲突与重试案例](./templates/06-punch-retry-cases.csv)

如果目前只有一个来源，只填一个来源即可。接口文档可在本机提供，密钥另行通过环境变量或密钥管理系统配置，不写入文档和仓库。

## 2. 当前系统真实能力

当前`POST /api/v1/attendance/punches`接收单条记录：

| 字段 | 当前要求 |
|---|---|
| `employment_id` | coreHR内部劳动关系UUID，必须已存在 |
| `punched_at` | 必须包含UTC偏移的日期时间 |
| `punch_type` | 可选，`in`或`out` |
| `source` | 来源代码，最长50字符 |
| `source_record_id` | 来源内稳定记录号，最长100字符 |
| `raw_payload` | JSON，当前可存储，但正式连接器必须改为白名单证据字段 |

系统按`source + source_record_id`判断重复并返回`duplicate=true`。当前实现遇到相同键但内容不同，也会返回旧记录；它还没有内容摘要冲突检测、外部员工号映射、批量接口、连接器认证和重试队列。因此不能直接把第三方报文原样接入生产。

## 3. 推荐统一契约

正式连接器进入coreHR前至少规范化为：

| 字段 | 规则 |
|---|---|
| `source_code` | 系统内配置的稳定来源代码 |
| `source_record_id` | 来源内永久稳定且可重放的事件ID |
| `source_employee_id` | 来源系统人员标识；连接器据此映射有效劳动关系 |
| `employee_number` | 来源能提供时保留，用于映射校验，不单独作为信任依据 |
| `occurred_at` | RFC 3339时间，必须带UTC偏移 |
| `event_type` | `IN`、`OUT`或`UNKNOWN` |
| `device_id` | 可选、受控长度；不得含密钥 |
| `evidence` | 仅保存已批准的设备、场所、定位结果等白名单字段 |
| `source_updated_at` | 来源支持更正时提供，必须带UTC偏移 |

外部系统通常不知道coreHR的UUID。连接器必须通过“来源代码＋来源人员标识”，并辅以工号，解析打卡时刻有效的唯一劳动关系；无匹配或多匹配均进入异常队列，不得猜测或默认写入。

## 4. 幂等、冲突和更正规则

- 同一`source_code + source_record_id`、同一规范化内容摘要：返回成功且标记重复，不再新增。
- 同一键、不同内容摘要：返回冲突并保留审计，不静默覆盖。
- 来源更正或撤销：以新事件引用原事件；原始证据不删除，日报重算产生新版本。
- 乱序和延迟记录允许写入；是否触发重算由考勤期间冻结状态和企业规则决定。
- 冻结期间继续接收原始证据，但不得自动改写已冻结日报/月报。

## 5. 认证、传输与存储边界

- 每个来源独立配置认证方式、凭证轮换、来源IP或签名校验；没有供应商文档前不冻结具体方案。
- 外部传输必须使用TLS；凭证只从运行环境注入，日志和审计中不得出现令牌或完整报文。
- `raw_payload`不能成为无限制的供应商报文仓库。正式适配时改为字段白名单、大小限制和保留期。
- 对敏感位置数据，必须先确认业务必要性、可见角色和保留期限；默认只保存判定结果。

## 6. 失败与重试

- 临时网络错误和服务繁忙：指数退避并带抖动，重试仍使用原`source_record_id`。
- 认证失败、字段错误、员工无法映射和内容冲突：不自动无限重试，进入可查询异常队列。
- 批量补传必须逐条返回结果，局部失败不能使成功记录回滚或重复新增。
- 当前代码仅有单条接口。是否增加批量入口或异步缓冲，以企业来源能力和压测证据决定；现阶段不引入应用服务器中间件。

## 7. 企业需要确认

1. 来源系统名称、数据方向（coreHR拉取/来源推送）和接口文档。
2. 来源人员标识、工号、事件ID、时间、进出类型对应哪个字段。
3. 时间字段是否含时区；不含时区时使用哪个来源固定时区。
4. 是否会补传、乱序、更正、撤销或重复发送。
5. 认证、签名、限流、单批上限和历史数据查询窗口。
6. 必须保留的设备/场所证据，以及哪些字段禁止落库。
7. 正常峰值和极端峰值：多少人、集中在多少秒内、允许多长延迟。

## 8. 验收最低案例

至少覆盖：正常入/出卡、无类型卡、重复重放、同键异内容、人员无匹配/多匹配、乱序、跨午夜、错误时区、冻结期补传、批次局部失败、认证失败和重试恢复。
