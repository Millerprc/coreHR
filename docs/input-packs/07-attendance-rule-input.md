# 企业输入包07：考勤、班次、假期与月结规则

> 状态：`TEMPLATE_READY / WAITING_FOR_ENTERPRISE_RULES`
> 输入顺序：第5项
> 数据安全：填写规则和合成案例，不填写真实员工、打卡位置、设备标识或请假原因

## 1. 本轮目标

把企业考勤制度转换为有类型、可版本化、可重算、可冻结并能用案例证明的规则。企业规则确认前，现有日报/月报只能用于工程演示，不能作为薪酬输入。

建议提供：

1. [规则集与适用范围](./templates/05-attendance-rule-sets.csv)
2. [班次](./templates/05-attendance-shifts.csv)
3. [计算规则矩阵](./templates/05-attendance-calculation-rules.csv)
4. [假期类型](./templates/05-leave-types.csv)
5. [假期计提与结转](./templates/05-leave-accrual-rules.csv)
6. [验收案例](./templates/05-attendance-scenarios.csv)

也可以直接提供现行制度、班次表和脱敏日报/月报样例；我会在本机拆成这些模板，并单列无法确定的规则。

## 2. 当前系统已经具备

- 考勤规则集草稿、版本、生效日期、IANA时区和发布。
- 普通/跨午夜班次、按员工和日期排班。
- 带时区的原始打卡，使用`source + source_record_id`幂等。
- 天/小时假期、请假、销假和通用流程实例关联。
- 不跟踪、记录允许负数、余额不足阻断三种假期余额模式。
- 不可变额度流水、人工发放/调整/结转/计提、审批扣减和销假冲回。
- 日报重算版本、月报聚合版本、月结冻结、特殊冻结和有因解冻。

## 3. 当前实际计算口径

在企业规则到达前，当前日报只执行以下通用逻辑：

- 班次起止时间计算计划分钟；跨午夜时结束日在次日。
- 打卡窗口固定为班次前后各6小时。
- 入卡取最早`in`，出卡取最晚`out`；无明确类型时退化为最早和最晚记录。
- 规则集只实际读取`late_grace_minutes`和`early_leave_grace_minutes`两个键。
- 规则集目前由班次直接引用，尚未实现个人、组织、法人、国家和默认范围的优先级解析。
- 休息分钟、弹性班次、取整、补卡和精细缺勤折算尚未进入计算器。
- 无打卡且无已批准请假记缺勤；只有一侧打卡记缺卡。
- 有完整打卡且有请假记`leave_with_punch`，尚未精细拆分半天或小时假。
- 月报按有排班、有工作分钟、已批准请假和缺勤状态做基础聚合。

这不是企业正式制度。模板确认后，应把规则从开放JSON收紧为有版本和校验的结构。

## 4. 必须确认的规则组

### 4.1 规则集和适用范围

- 规则集适用于哪些国家、法人、组织、人员类型或个人例外。
- 多个范围同时命中时的优先级：建议`个人 > 组织 > 法人/国家 > 默认`。
- 时区、工作日历、法定节假日和调休来源。
- 规则变更如何处理已发布排班和历史结果；默认不重算冻结历史。

### 4.2 班次和打卡窗口

- 上下班、跨午夜、休息时间、弹性窗口和计划工时。
- 最早入卡、最晚出卡、重复打卡、无类型打卡和跨班次归属。
- 班次前后取卡窗口；不能继续固定为6小时而不经确认。
- 临时换班、取消排班、休息日加班和无排班打卡的处置。

### 4.3 迟到、早退、缺卡和缺勤

- 迟到/早退宽限分钟、分钟取整、多个档位和封顶。
- 缺一侧卡是否整日异常、可否补卡、补卡审批后如何重算。
- 缺勤判定是否看打卡、请假、出差、外勤或其他事件组合。
- 半天缺勤、小时缺勤和跨日异常如何折算。

### 4.4 请假和销假

- 每个假类按自然日、工作日、排班分钟还是固定天数计算。
- 最小申请单位、半天分段、跨班次、跨时区和跨年度规则。
- 是否允许负数、余额不足是否阻断、审批前是否预占。
- 请假与打卡并存、重叠申请、撤回、驳回、销假和补录规则。

### 4.5 自动计提和结转

- 年初、月度、入职周年或人工触发。
- 按员工类型、工龄、入职月份、转正状态的额度和折算。
- 封顶、清零、结转上限、结转有效期和离职处理。
- 历史修订采用新增流水，不修改原流水。

### 4.6 日报、月报和冻结

- 日报字段、异常码、天/小时折算和审批结果截止时间。
- 月报生成日、复核期、冻结时点、允许操作角色和更正流程。
- 月结冻结覆盖完整自然月；特殊业务冻结的触发条件和范围。
- 解冻、重算、复核和重新冻结均必须填写原因并保留原版本。

## 5. 规则优先级建议

同一工作日的计算建议固定为以下顺序，企业不同意时需明确替代顺序：

1. 找到目标日期有效劳动关系和时区。
2. 解析有效排班、班次和工作日历。
3. 归属原始打卡，不修改原证据。
4. 叠加已批准的请假、销假、出差/外勤等事件。
5. 应用迟到、早退、缺卡和缺勤规则。
6. 生成新日报版本和证据引用。
7. 月报只聚合当前日报版本。
8. 冻结后禁止日报/月报重算，但继续接收原始打卡证据。

## 6. 验收案例要求

规则文字之外至少提供下列合成案例，每个案例填写预期状态、分钟和异常码：

- 正常班、迟到宽限内/外、早退宽限内/外。
- 无卡、缺入卡、缺出卡、多次卡、无类型卡。
- 跨午夜、班次边界附近、夏令时地区。
- 整天假、半天假、小时假、请假与打卡并存、批准销假。
- 无排班打卡、休息日、法定假日、临时换班。
- 月结冻结、解冻重算和修订版本。

系统是否符合企业制度，以案例通过为主证据，不只看规则配置页面。

## 7. 明确延期

- 考勤结果进入薪酬、缺勤扣款和加班费属于第四阶段。
- 一万人同时打卡/查询需要打卡接口和流量模型后专项压测。
- 企业微信、设备或第三方平台的认证、补传和重试见后续打卡接口输入包。
