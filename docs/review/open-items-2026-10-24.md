## A. 需要你拍板才能继续的产品语义

### A 组 1 · BPMS 审批引擎

#### A1（⚠️）加签后原审批人是否还要再签一次？

- **现状**：引擎层「加签」＝ 当前任务终结 + 在同一节点生成一条新的待办（与转办机制相同，差异只在动作值与审计记录）。
- **问题**：Moka 与主流 OA 的加签通常是「加一个人一起签」，**原审批人仍要签**；当前实现是「换人签」。
- **若你要求「原审批人仍要签」**：需要改会签计算规则（同一节点的待办聚合规则），工作量在 `state_machine.py` + 会签判定处，不在接口层。
- **不拍板的后果**：加签语义会与用户预期不符，且后续接真实审批时必然返工。

#### A2（⚠️）退回的目标节点范围

- **现状**：只允许退到「上一个审批节点」。
- **可选**：①维持现状；②允许退到任意历史节点；③由发起人指定节点。
- **不拍板的后果**：②③都需要改路由回溯逻辑与权限校验。

#### A3（⚠️）撤销 / 取消在业务对象上的终态

- **现状**：人事事件与批量异动只有 `ready / rejected` 两态，**撤销、取消与驳回在业务对象上同态**；语义区分只体现在审批实例终态（`withdrawn` / `cancelled` / `rejected`）与流转历史上。
- **可选**：①维持现状；②把「已撤销 / 已取消」拆成独立业务终态（需要业务对象侧加状态词表与联动）。
- **不拍板的后果**：用户在业务单据上看不出「撤销」和「驳回」的区别，与 D-095「三者必须完全区分」的精神有落差（接口与审计层已区分）。

### A 组 2 · 人员基础信息治理（【编辑】/【修正】）

#### A4（⚠️）规范冲突留痕：`07`/`08` 号文档的「引导使用更正事件」vs 本轮【编辑】/【修正】拆分

- **冲突点**：`docs/01-foundation/07-*.md:249` 与 `08-*.md:169` 仍写着「界面引导使用更正事件」，而本轮按 D-105 把人员基础信息拆成两个动作：
  - 【编辑】＝ 直接改主档并保存（不产生更正事件）；
  - 【修正】＝ 填写生效日期写入修正版本（**保留** `PERSON_CORRECTION` 事件通道作为审计/流程载体）。
- **我已做的处理**：按拆分语义实现，同时保留更正事件通道不删。
- **需要你确认**：是否更新 `07`/`08` 号文档的相关表述，还是保留「更正事件」作为另一种用法（独立入口）。

#### A5（📎）历史花名册的「字段级历史」精度限制，是否接受

- **事实**：历史花名册的人员字段时点值 = 登记值 + 生效日期 ≤ 查询日期的最后一条修正。**没被修正过的人，其时点的姓名/证件等于当前值。**
- **含义**：这不是完整的历史回放，精度取决于修正记录覆盖率。界面已用提示条明说，未做「快照还原」。
- **可选**：①接受（当前实现）；②新建独立的「人员字段历史」表（每次修改都留痕，与修正解耦）——代价是每人每次改字段多一行写入。
- **不拍板的后果**：用户可能误以为花名册能回看到任意历史字段。

#### A6（📎）Moka 对标只做「功能结构」，不做「可配置性深度」

- Moka 的产品深度主要在 `/setting` 的 161 条可配置路由（占全站 40%），coreHR 本轮**完全没碰设置模块**。
- 本轮的五项复刻对齐的是**功能结构与信息层级**。
- **需要你确认**：是否接受「先补功能结构、设置模块另立项」。

#### A7（⚠️）人员修正：一条修正是否支持一次改多个字段？

- **现状**：**一条修正只改一个字段**（表单是「待修正字段 + 修正后值」）。改 3 个字段要提交 3 次，产生 3 个生效日期版本。
- **可选**：①维持「一条一字段」；②一条修正可携带多字段（需要给 `person_field_versions` 加批次号，或一条记录存 JSON 字段集）。
- **不拍板的后果**：批量纠正历史信息时操作次数偏多；②会改变「同一人 + 同字段 + 同日冲突」这条校验的粒度。

#### A8（⚠️）人员修正：生效日期下界口径

- **现状**：下界 = **最早雇佣生效日**（`actual_start_date or planned_start_date` 的最小值）；无雇佣记录时退化为「主档登记日」。
- **副作用**：**尚未入职**（计划入职日在未来）的员工**无法往过去补录**修正。
- **可选**：①维持；②改用「主档登记日」；③两个下界取其一（例如取较早者，允许补录但不得早于雇佣锚点）。
- **不拍板的后果**：补录历史信息时会被 422 `PERSON_CORRECTION_EFFECTIVE_DATE_TOO_EARLY` 挡住，且报错信息不解释原因。

#### A9（⚠️）人员修正：是否需要独立权限码与必填变更原因？

- **现状**：修正**沿用 `PERSON_EDIT_BASIC`**，**未新增独立权限码**；变更原因**选填**。
- **规范对照**：`docs/01-foundation/08-人事数据与事件规范.md:173` 要求「紧急更正需要独立权限、原因和审计」。
- **已做的折中**：审计层做了字段级脱敏（姓名只留首尾、出生日期只留年份），既满足 `07:248` 的「记前后值」，又不违反 `07:10` 的脱敏要求与既有测试断言。
- **可选**：①维持现状；②新增 `PERSON_CORRECT` 独立权限码（需补迁移 seed）；③变更原因改必填。
- **不拍板的后果**：与 `08:173` 存在明文偏差，且「谁能改历史信息」与「谁能改当前信息」是同一枚码。

#### A10（⚠️）规范冲突：基础档案更正要不要走工作流执行链？

- **冲突点**：`08-人事数据与事件规范.md:58` 把「人员基础档案更正」列为**第一阶段必须承载的业务事件**（即走事件/审批链）。
- **本轮实现**：【修正】**不进入**工作流事件执行链，直接落 `person_field_versions` + 一条 `status=completed` 的 `PERSON_CORRECTION` 事件（工作流模块的事件校验只认 employment/contract）。
- **需要你确认**：①接受「修正不走审批」（当前实现）；②把修正接入 BPMS 审批链（需 BPMS 引擎支持「非 employment/contract 对象类型」的事件）。
- **不拍板的后果**：文档与实现的「更正＝一个走流程的事件」这一条不一致，后续接真实审批时会返工。

### A 组 3 · 权限落差（本轮 P-13 / P-14 已落地，以下是残留）

#### A12（⚠️）汇报关系：人员下拉是否需要独立的只读候选人端点？

- **现状**：下拉数据源是 `GET /api/v1/workforce/persons`，该端点要求 `PERSON_VIEW` **且** `PERSON_SENSITIVE_VIEW` 同时持有（`require_permissions` 是「全部满足」语义）⇒ 只持 `ORGANIZATION_VIEW` 的账号下拉**静默显示「未找到匹配人员」**。

- **现状**：标签的读写**同权**（都要求 `WORKFORCE_ADMIN`），页签仅在管理员可见时挂载 ⇒ 只读角色看不到任何标签。

### A 组 4 · 消息引擎（一期已落地，以下是未拍板的四条）

- **现状**：站内信是**尽力型**（消息落库即送达，Worker 失败只重试 5 次，无人工兜底）。

#### A17（📎）未读提醒的重复策略

- **现状**：SSE 只在消息入库时推一次，**不重复提醒**。

#### A18（📎）模板与文案的所有权

### A 组 5 · 兼岗（person 级载体，D-104）

#### A19（📎）职务是否要加真列（`organization_person_relations.job_id`）？

- **现状**：`organization_person_relations` 表**没有 `job_id` 列**，而本轮明确不新建表、不加迁移 ⇒ 职务引用（`job_id`/`job_name`）、变更原因、来源事件 id 统一编码进 `note`（JSON，`String(500)`）。

- **需要你给的**：SSC 是否需要发起某几类人事事件（例如转正、调岗、异动）；若需要，是否接受为此新增「发起某类人事事件」的细粒度权限码（而不是给域级 `LIFECYCLE_ADMIN`）。

- **需要你给的**：是否认可「等有真实慢查询数据再收敛」。**工程侧不自行删除既有索引** —— 删除会让依赖单列索引的执行计划在数据量大的库里变慢，而目前没有慢查询证据支撑这个判断。

#### A29（⚠️）事件生效「毒丸」行为：坏事件要不要挡住其余事件？

- **现状**：组织版本事件在**生效落库前**会复校上级有效性等约束（本轮 C6 B 组新增）。复校不过时该事件抛错 → **整个 `apply-due` 请求失败，同批其他到期事件也不再生效**（事件保持 `planned`）。
- **这是"必须抛错"的直接后果**：要么整批回滚，要么跳过坏事件继续处理其余。
- **需要你给**：①整批失败（当前行为，安全但一条坏数据挡住全月生效）；②跳过坏事件、把它标成「待人工处理」并继续处理其余（更可用，但要定义这个新状态）。

#### A30（⚠️）考勤月报口径缺口（含一项企业口径）

- **现状**：`attendance/extended_service.py` 的月报只累加「有排班的日子」的日报；`leave_with_punch`（请假且有打卡）**不计入请假天数**、`exception`（缺卡 / 迟到早退）**既不计入缺勤也不单独统计**、**未排班日完全不在统计范围**。
- **可自定部分**（工程侧可直接修）：`leave_with_punch` 计入请假天数、`exception` 拆成「缺卡」与「迟到早退」两项分别统计。
- **需要你给的**：**未排班日算不算缺勤**？这属企业规则，工程侧不能自定（会直接影响缺勤天数与工资扣款）。
- **附带**：修复后月报需要新增分项字段（异常天数、未排班天数），要再写一条迁移。

#### A31（📎）后台任务 Worker 的部署形态

- **现状**：任务框架已落地（任务表 + 独立 Worker 进程 + 退避重试 + 管理查询与手动重试）。**本轮已在 `deploy/compose.yaml` 增加 `worker` 服务**（与 api 同镜像、独立进程），本机 `docker compose up -d worker` 即可让任务真正被执行 —— 批量考勤计算（**D-116**）依赖它，任务没人执行就会一直挂在 `pending`。
- **仍未定**：生产上 Worker 怎么托管（compose 服务 / systemd / k8s），以及要不要在 API 启动时自动拉一个（**当前刻意不挂 API 启动路径**，PRD 要求长任务走独立进程）。
- **需要你给的**：生产上 Worker 用哪种托管形态。本机 compose 这套是开发与演示形态，不等于生产形态。

#### A35（📎）批量考勤计算的三处规模化残留（D-116 之后）

- **现状**：D-116 已把「逐人单选」改成「范围三态 + 后台任务」，200 人规模不再要点 200 次。**已解决的**：默认全员、多选指定、排除指定、一次提交覆盖整个范围、后台执行、提交时冻结预检、单人失败隔离、长任务续租。
- **残留一 · 人员下拉单页上限 200**：`GET /attendance/employment-options` 的 `limit` 上限是 200，排序按工号。**300 人公司**在前端只能看到工号靠前的 200 人，必须靠姓名/工号搜索逐个添加，**没有「按部门/按在职状态批量勾选」**。前端已在人数口径行提示「当前只加载了前 200 人」，但根治要后端出「按条件全选」端点（传条件、不传 id 列表）。

- **残留三 · 范围语义的两处不一致**（需要你拍板）：①`scope=selected` 里有不存在的 id → **整单 422**（`ATTENDANCE_CALCULATION_TARGET_INVALID`）；`scope=excluded` 里有不存在的 id → **静默忽略**。同一份误选动作两种结果，建议统一为「忽略 + 在 `failure_codes` 里计数」。②「排除人员」在页面上显示的是**提交时的选择数**，后端忽略不存在的 id 后**实际排除数可能更小**，两处口径有轻微差异（成功结果以 `result` 为准）。
- **附带未做**：任务历史**刷新页面即清空**（无任务列表页、无失败任务重试按钮）；「全员」口径含已离职人员，界面上**没有在职/离职标识**（按你「不要自行加工选项文案」的要求没加）。
- **需要你给的**：上面三条里，哪条要先做。
