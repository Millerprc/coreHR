# coreHR 第一至第三阶段整体 Review 指南

> 版本日期：2026-08-09
>
> 适用对象：业务规则确认人、HR 系统主管理员
>
> 目标：核对“已确认需求—正式文档—管理端功能—数据库结果—当前边界”是否一致

## 1. 建议 Review 时间

建议预留 **5 小时**做一次完整 Review；如果只检查核心主链，可压缩到 **3 小时**。

| 环节 | 完整 Review | 核心 Review |
|---|---:|---:|
| 环境、账号和资料准备 | 20 分钟 | 15 分钟 |
| 公共能力与第一阶段 | 90 分钟 | 55 分钟 |
| 第二阶段 | 80 分钟 | 50 分钟 |
| 第三阶段 | 80 分钟 | 50 分钟 |
| 文档匹配、缺口和结论记录 | 30 分钟 | 10 分钟 |
| 合计 | **300 分钟** | **180 分钟** |

完整 Review 建议拆成两次，避免连续操作导致判断疲劳：

- 第一次约 2 小时 30 分：环境、公共能力、第一阶段。
- 第二次约 2 小时 30 分：第二、第三阶段和结论确认。

这 5 小时是你的业务 Review 时间，不包含开发修复时间、正式数据清洗时间或万人容量压测时间。

## 2. Review 前准备

1. 按[业务运行手册](../implementation/business-runbook.md)启动本机业务环境。
2. 打开主管理员工作台：`http://127.0.0.1:5173/business.html`。
3. 同时打开[实现符合性审查](./phase-1-3-implementation-conformance-review.md)，以其中的 `PASS/PARTIAL/HOLD` 为完成度口径。
4. Review 数据统一使用 `UAT-` 或 `REVIEW-` 前缀的合成数据，不使用真实姓名、证件、电话、合同原文或薪酬信息。
5. 为每个检查项记录：`通过 / 不通过 / 规则待确认 / 本期不验收`，并附页面截图或记录编号。

建议记录表：

| 编号 | 检查项 | 结果 | 记录编号/截图 | 问题描述 | 是否阻塞本阶段 |
|---|---|---|---|---|---|
| 示例 | 新建未来生效组织 | 通过 | `REVIEW-ORG-01` | — | 否 |

## 3. 完成度判断原则

- 页面能打开但不能形成业务结果，不算通过。
- 形成结果但没有原因、版本或审计记录，不算通过。
- 通用能力已实现、企业字段或规则尚未提供，记为 `规则待确认`，不要记成系统缺陷。
- 已明确延后到第五阶段的 MySQL、Oracle、多租户和 Apusic 等中间件，不进入本轮失败项。
- 第三阶段的技术考勤结果在企业规则确认前不能作为薪酬依据。

## 4. 公共能力与第一阶段 Review（90 分钟）

### 4.1 登录、权限、错误和审计（15 分钟）

| 操作 | 预期结果 | 对应文档 |
|---|---|---|
| 使用主管理员登录并进入 9 个开放菜单 | 所有菜单可进入，无业务 4xx/5xx | 技术架构基线、符合性审查第 3/7 节 |
| 提交一个缺少必填字段的表单 | 页面明确提示字段问题，不生成半成品记录 | 代码与接口规范 |
| 完成一项带“原因”的修改 | 结果可回看，后台审计保存操作人、原因、Trace ID 和前后值 | 项目决策、符合性审查平台能力 |

### 4.2 配置、组织和财务维度（30 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 新建 `REVIEW_` 字典及字典项 | 稳定代码唯一，可启停和维护层级 | 正式码表仍需企业确认 |
| 新建组织类型、法人和两级组织 | 每个组织同一有效期间只有一个上级 | 组织类型支持自定义 |
| 为组织创建未来生效版本 | 当前日期仍显示当前树；到未来日期可取得新版本 | 管理端只展示有效组织树 |
| 维护组织—法人多对多关系 | 一个 BU 可对应多个法人，关系有独立有效期 | 法人与组织不强绑定为一对一 |
| 维护负责人、BP、成本中心分摊和收入目标 | 三类负责人可并列；分摊合计校验；收入目标按年/月和币种保存并向上汇总 | 分摊只汇总，不核算/折算 |

### 4.3 人员、关系、工号和任职（25 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 创建一名合成人员并预留工号 | 工号为六位纯数字流水号 | 不使用真实个人信息 |
| 创建待入职劳动关系 | 计划入职日期明确，工号被占用 | 正式/校招生是否占编由配置决定 |
| 尝试给同一自然人在重叠期间创建第二条法人劳动关系 | 系统拒绝 | 协议关系可以并存 |
| 添加主任职、兼岗或借调 | 主任职同日唯一；其他关系按类型并存 | 变更应通过人事事件维护 |
| 打开人员档案 | Person、劳动关系、组织职务和协议关系分别呈现 | 正式档案字段仍待字段验收表 |

### 4.4 编制、招聘和数据治理（20 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 选择年月维护编制 | 月度值平铺、版本递增 | 编制是结果展示，不强卡招聘 |
| 生成月初/月末快照 | 月均为 `(月初 + 月末) / 2` | 年度展示当前值 |
| 创建招聘需求 | 可查看编制参考，但无空编也不阻断 | 已确认弱关联 |
| 下载 CSV 模板、提交含未知列的文件 | 预校验拒绝未知列，不写入 | 当前只开放六类非敏感主数据 |
| 重复提交同一来源和内容 | 幂等跳过，不重复建档 | 来源内容改变时当前拒绝并待确认更新策略 |

第一阶段 Review 结束时，应能回答：组织、法人、人员、劳动/协议关系、任职、编制和招聘需求是否按已确认关系拆分；哪些缺口只是正式码表/字段/迁移资料尚未提供。

## 5. 第二阶段 Review（80 分钟）

### 5.1 流程与人事事件（30 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 建立含开始、审批、结束节点的示例流程并发布 | 非法或歧义流程不能发布；合法流程生成版本 | — |
| 建立一条条件审批线和一条默认线 | 满足条件时走条件审批；不满足时走默认审批；选路历史可回看 | 判断字段和值按真实流程图配置 |
| 分别验证会签和或签 | 会签全部通过后推进；或签任一通过后推进并关闭其他待办 | 真实审批人规则待流程图 |
| 创建今天和未来日期的人事事件 | 今天直接生效；未来事件进入待执行队列 | 审批完成的未来离职按未来日期释放结果 |
| 回退一个已生效事件 | 新增回退事件，原事件和审计不删除 | 回退也支持审批和未来生效 |

### 5.2 候选人、应聘和录用（20 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 建候选人并关联招聘需求 | 应聘状态可按筛选、面试、Offer 推进 | — |
| 在 Offer 阶段确认录用 | 同一事务创建/复用 Person、六位工号、待入职劳动关系和招聘组织对应主任职 | 编制不阻断录用 |
| 重复提交同一录用请求 | 返回同一转换结果，不重复分号或建档 | 再次入职复用原 Person/工号 |

### 5.3 合同/协议生命周期（30 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 建立劳动合同并关联劳动关系 | 关联关系必须属于同一 Person；版本为 V1 | 劳动关系与协议关系二选一 |
| 建立合作/派遣等协议并关联协议关系 | 可以与劳动合同并存 | 正式协议类型代码待确认 |
| 设置近期结束日和提醒天数 | 进入提醒期后在页面顶部展示 | 正式提醒对象/渠道待确认 |
| 执行变更 | 到期日、提醒等结果改变，版本递增，事件可追踪 | 至少修改一个值 |
| 执行未来解除 | 先显示待执行；到生效日处理后变为已解除 | 不提前改写正式结果 |
| 执行续签 | 创建后继合同，原合同标记已续签，前后链路保留 | 新合同生效日晚于原结束日 |
| 回退解除或续签 | 新增回退事件；前值恢复；续签后继合同被取消 | 不删除原动作；多个动作按执行顺序逆序回退 |

合同 Review 时同步打开[企业输入包 02](../input-packs/02-contract-agreement-fields-and-attachments.md)。页面未包含企业正式字段和附件归档属于已知输入缺口，不应误记为通用生命周期失败。

## 6. 第三阶段 Review（80 分钟）

### 6.1 规则、班次、排班和打卡（25 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 建立带 IANA 时区的考勤规则并发布 | 规则版本固定；月份边界按时区解释 | 默认 `Asia/Shanghai` |
| 建立普通/跨日班次并排班 | 班次引用已发布规则；跨日标识正确 | 企业迟到早退细则待确认 |
| 重复提交同一来源幂等键的打卡 | 不产生重复原始打卡 | 原始打卡作为不可变证据保留 |

### 6.2 请假、销假和余额（25 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 分别建立不跟踪、允许负数、余额不足阻断假类 | 三种模式行为不同且明确 | 单位建立账户后不可修改 |
| 发放额度并批准请假 | 产生不可变扣减流水和新余额版本 | 人工入账必须有原因和幂等键 |
| 批准销假或取消已批准请假 | 产生冲回流水，不修改原扣减流水 | 跨年度受管假期当前需拆单 |

### 6.3 日报、月报和冻结（30 分钟）

| 操作 | 预期结果 | 关键边界 |
|---|---|---|
| 计算日报并重复重算 | 生成新版本，保留异常证据 | 企业规则未确认前仅技术验收 |
| 聚合月报 | 由当前日报形成；缺失日报可补算 | 不直接作为薪酬输入 |
| 冻结完整自然月并尝试重算 | 日报/月报重算被阻止；原始打卡仍接收 | 月结冻结必须覆盖完整自然月 |
| 有因解冻、重算、再次冻结 | 每一步均保留操作原因和审计 | 不提供物理删除 |

## 7. 文档—系统匹配 Review（30 分钟）

按以下顺序核对，发现不一致时优先以代码和实际运行事实为证据，再修正文档：

1. [项目决策](../01-foundation/03-项目决策.md)：检查已确认业务口径是否被实现或明确标为待输入。
2. [实现符合性审查](./phase-1-3-implementation-conformance-review.md)：检查每项 `PASS/PARTIAL/HOLD` 是否与实际操作一致。
3. [交付回执目录](../delivery/)：检查每个已实现闭环是否有范围、边界和验证证据。
4. [企业输入包目录](../input-packs/)：检查未完成项是否确实需要企业资料，而不是代码遗漏。
5. [业务运行手册](../implementation/business-runbook.md)：检查启动、登录、数据治理和停止步骤是否可复现。
6. `tmp/ui-mockup/06-nav-system.html`：只复用其模块分组、侧栏层级、工作区切换和搜索交互作为后续导航信息架构参考；现阶段管理端继续使用 Ant Design 组件和既有页面壳，不直接复制原型 CSS。

## 8. 本轮可批准与不可批准的结论

完成上述 Review 且没有阻塞缺陷时，可以批准：

- 主管理员工程 MVP 进入业务 UAT。
- 一至三阶段通用核心链路与当前正式文档一致。
- 后续按输入包逐项补充企业码表、字段、流程和考勤规则。

本轮不能批准：

- 替换生产系统或导入完整真实数据。
- 普通员工、自助端和细分数据权限开放。
- 合同附件正式归档、电子签章或真实审批链完成。
- 考勤结果进入薪酬。
- 一万人并发、灾备、多租户、MySQL/Oracle 或 Apusic 兼容性达标。

Review 完成后，只需把问题按“系统缺陷 / 企业规则待确认 / 数据待提供 / 第五阶段事项”四类反馈。这样可以直接转成后续最小开发任务，不会把业务输入缺口和程序缺陷混在一起。
