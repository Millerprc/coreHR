# coreHR 第一阶段领域产品化设计

> 状态：已批准，待实施
> 日期：2026-08-08
> 适用范围：第一阶段组织、人事、编制和招聘需求
> 依据：`docs/01-foundation` 已确认需求、ADR-0002、现有第一至三阶段可运行切片

## 1. 决策摘要

coreHR 是全新的实验性产品，不承担旧 EHR 的兼容替换、双写或历史重建责任。旧 EHR 表结构仅用于识别真实字段、关系和异常案例；真实样例数据不得进入源码、测试、提交记录或前端构建产物。

第一阶段采用领域产品化路线：稳定业务对象使用明确关系模型，关键规则由数据库约束和领域服务共同保证，枚举通过数据字典配置。不得通过复制旧表、通用 JSON 或无约束动态表单绕过领域建模。

第一阶段只交付 PC 管理端，首批用户为 HR 系统主管理员和 SSC。员工自助、移动端、MCP、多租户、多语言、多数据库运行时和万人并发专项验证不在本阶段范围。

## 2. 目标与完成定义

第一阶段完成后，管理员能够在同一个产品内：

1. 配置字典、组织类型、人员类型和占编规则。
2. 维护当前及未来生效的组织树、法人、负责人、BP、成本中心和收入目标。
3. 维护职务体系、月度编制、冻结、人数结果和月初月末快照。
4. 建立人员档案、劳动关系、协议关系、任职、汇报和四类主体历史。
5. 管理招聘需求，但不把招聘需求与编制强绑定。
6. 批量导入导出第一阶段数据，并查看批次错误和审计记录。
7. 分别查询当前结果、未来计划和任意有效日期的历史结果。

“存在数据表”或“页面可以打开”不算完成。每个模块必须具备数据库迁移、领域校验、REST API、管理页面、权限审计、自动化测试和可重复 UAT。

## 3. 模块边界

### 3.1 配置中心

负责数据字典、字典项、组织类型、人员类型、雇佣状态、协议类型、负责人类型、BP类型、国家地区、币种及占编规则。

- 业务记录保存稳定代码，不保存显示名称作为事实主键。
- 字典项可停用但不可因已被引用而物理删除。
- 显示名称修改不改写历史业务记录。
- 正式员工和校招生默认占编，其他类型默认不占；规则按生效日期版本化。

### 3.2 组织与主体

负责组织本体、组织有效版本、法人、组织与法人关系、负责人、BP服务关系、汇报关系、成本中心分摊和收入目标。

- 每个业务组织只能有一个直接上级，组织树禁止成环。
- 组织类型预置集团、BG、BU、部门，同时允许配置新类型。
- 组织编码自动生成；导入历史编码时不得重复，自动编号必须避开已占用编码。
- 组织与法人为多对多关系；一个 BU 可以关联多个法人。
- 每个组织可以有三名无主次负责人。
- BP支持 HRBP、EBP、TBP、FBP；同一人员可以服务多个组织，但只能属于一个BP类型。
- 同一组织在同一有效期间的成本中心分摊合计必须为100%。
- 收入目标保存币种、年度总额和12个月明细；月度合计必须等于年度总额。
- 收入目标从叶子组织按币种向上汇总，不进行汇率折算。

### 3.3 职务、编制与人力结果

负责职务、职级、职等、职类、序列，月度编制版本，占编规则，冻结和人数快照。

- 职务是任职和编制的直接维度；职级、职等、职类、序列分别保存为可配置代码。
- 编制按组织×职务×月份平铺维护，修改指定年月时创建新版本，不覆盖旧版本。
- 编制只呈现结果，不阻断招聘需求，也不要求招聘需求绑定空编。
- 待入职人员从计划入职日期起计入结果；调岗、离职和撤回入职的生效结果释放原归属。
- 月初人数、月末人数、月均人数和当前人数分别展示；月均为`(月初+月末)/2`，年度页面展示当前值。
- 月结冻结和业务冻结并存。业务冻结可按年月、组织、职务任意组合，空维度表示全部范围。
- 普通角色不得修改命中冻结范围的数据；授权绕过必须填写原因并记录审计。
- 月初月末快照依据可配置 IANA 时区生成。修订创建新版本并关联原批次。

### 3.4 人员与雇佣

负责自然人、人员子档案、劳动关系、协议关系、任职、汇报、四类主体和人员标签。

- `Person`表示永久自然人身份，离职不得删除。
- `Employment`表示一次劳动关系；二次入职创建新记录并恢复原六位工号。
- 同一自然人在重叠有效期间只能有一条集团内法人劳动关系。
- 合作、劳务派遣等非劳动关系使用独立协议关系，可以与劳动关系并存。
- 创建待入职档案时分配六位纯数字工号；已分配工号永不回收给其他自然人。
- 每个员工同一时点只有一个主组织、一个主职务和一个实线上级；虚线上级允许多个。四类主体默认相同，管理员可以分别调整。
- Person子档案包含证件、联系方式、紧急联系人、教育经历和工作经历，不使用通用 JSON 保存这些业务事实。
- 未来生效变更保留计划版本；生效前不得改变当前结果。
- 基础档案允许授权管理员直接更正并记录前后值；核心人事关系引导通过人事事件处理。

### 3.5 招聘需求

负责招聘需求本身，不包含候选人、面试、Offer和录用。

- 需求包含组织、职务、需求人数、期望到岗日期、原因和状态。
- 第一阶段状态为草稿、已通过、招聘中、已完成、已取消。
- 保留审批中、已驳回和已撤回状态代码，但第一阶段不创建审批实例。
- 页面展示相关编制和人数结果，但超编不阻止创建或推进需求。

### 3.6 数据治理

负责导入批次、行级错误、导出、数据更正、审计、敏感访问和待同步事件。

- 导入必须先整批解析和校验，再由用户确认提交。
- 校验失败的行不得产生半条业务记录；批次保存成功数、失败数和错误码。
- 同一导入文件和业务幂等键重复提交不得创建重复数据。
- 所有高风险写操作记录操作者、原因、来源、前值、后值和Trace ID。
- 待同步事件在业务事务内写入 outbox，后续企业微信、OA和下游接口异步消费；第一阶段不接真实下游。

## 4. 分层与数据流

后端保持以下单向依赖：

```text
API/Schema
  → Application Use Case
    → Domain Policy/Validator
      → Repository/SQLAlchemy
        → PostgreSQL
```

API不得直接拼装跨实体业务状态。领域服务不得依赖HTTP请求对象。数据库会话、权限上下文、时钟和编号服务通过明确接口注入。

写操作流程：

```text
鉴权
→ 动作权限与数据范围校验
→ 输入及引用对象校验
→ 生效日期、重叠、冻结和状态规则校验
→ 单事务写入业务事实、历史版本、审计和outbox
→ 返回新版本及可追溯标识
```

读操作分为：

- 当前查询：返回当前有效结果。
- 时点查询：必须传入`effective_at`并返回命中版本及有效区间。
- 未来查询：返回待生效事件或计划版本，不混入当前结果。
- 快照查询：只读取指定快照批次，不用当前数据重新计算冒充历史。

## 5. 数据模型调整

保留现有模型作为第一版骨架，并完成以下调整。

### 5.1 新增明确实体

- `person_documents`
- `person_contacts`
- `person_emergency_contacts`
- `person_educations`
- `person_work_experiences`
- `revenue_target_months`
- `import_batches`
- `import_rows`
- `sensitive_access_logs`
- `outbox_events`

### 5.2 强化现有实体

- 组织、任职、汇报、主体、成本分摊和占编规则增加有效期不重叠约束。
- 当前版本使用数据库可验证的唯一条件，不只依赖`is_current`布尔值。
- 成本分摊100%和收入目标12个月合计在领域服务提交时校验，并用并发锁保护同一业务键。
- `revenue_targets.monthly_amounts` JSON迁移为12条月度明细，避免无法约束和查询。
- 人员敏感字段与普通字段分表，密文、检索指纹和脱敏展示值职责分离。
- `source_event_id`使用真实外键关联人事事件或使用明确的多态来源表，不保留无约束UUID。

### 5.3 删除语义

- 主数据和历史事实默认不物理删除。
- 尚未被引用且处于草稿状态的记录可以取消；取消仍保留审计。
- 导入产生的错误行可以按保留策略清理，但不得删除已提交业务事实。

## 7. 关键业务流程

### 7.1 未来组织变更

管理员创建变更草稿并指定生效日期。系统验证单父、无环、上级有效期和相关主体关系，随后生成待生效版本。调度器在生效时区到达目标日期后，以幂等任务关闭旧版本、启用新版本并写入审计和outbox。失败进入可重试异常队列，不静默跳过。

### 7.2 二次入职

管理员先按可信证件指纹搜索自然人。系统给出重复候选，由SSC确认。确认后创建新的Employment，恢复该Person原工号，并检查劳动关系有效期不得重叠。协议关系不参与劳动关系唯一性限制。

### 7.3 编制与快照

管理员选择年月维护组织和职务的月度编制。提交时检查冻结和版本并发。快照任务在配置时区边界读取当时有效的人员、任职、职务和占编规则，生成不可变批次及明细。修订以原批次为父级创建新版本。

### 7.4 导入

用户下载带版本号的模板，上传后系统创建导入批次并异步解析。系统展示逐行错误、重复候选和影响摘要。用户确认后按依赖顺序分事务批量提交；失败批次可修正重试，已成功业务键保持幂等。

## 8. 权限与安全

首版仍优先主管理员，但权限模型必须支持后续自定义角色。

- 功能权限：查看、新增、修改、取消、导入、导出、冻结、解冻、回退、查看历史。
- 数据范围：全部、组织及全部下级、法人、未来BP服务范围。
- 字段权限：基础查看、敏感查看、明文查看、敏感修改、导出和打印。
- 高风险权限：绕过冻结、快照修订、明文导出和人员关系更正。

证件号码和银行账户等字段采用AES-256-GCM应用层信封加密：每条敏感记录使用随机数据密钥，数据密钥由版本化主密钥包装；主密钥仅从运行环境注入，不得存入数据库或仓库。精确匹配字段使用独立密钥生成HMAC-SHA-256检索指纹。页面默认脱敏，明文查看使用短时授权并单独记录访问目的。日志、缓存、异常和导出临时文件禁止出现明文。

## 9. 错误与并发处理

领域错误使用稳定错误码，至少覆盖：

- 有效期重叠
- 组织成环或上级无效
- 成本分摊不等于100%
- 年度与月度目标不一致
- 劳动关系重叠
- 工号耗尽或冲突
- 命中冻结
- 版本并发冲突
- 导入模板版本错误
- 敏感字段权限不足

写接口接收幂等键和期望版本。版本不一致返回冲突，不使用最后写入者覆盖。批量任务使用明确批次状态、重试次数和错误明细，不吞错。

## 10. API原则

- 正式业务接口统一位于`/api/v1`，移除或兼容迁移当前无版本前缀的试验接口。
- 列表支持分页、排序、筛选和`effective_at`。
- 创建、版本变更、取消、回退和高风险查看使用独立动作接口，不用一个万能更新接口表达。
- 错误响应包含错误码、用户可读信息、字段路径和Trace ID，不返回内部堆栈。
- OpenAPI示例只使用合成数据。

## 11. 测试与验收

### 11.1 自动化层级

- 单元测试：日期重叠、组织无环、100%分摊、目标合计、占编、状态机和脱敏。
- 数据库测试：排他约束、唯一当前版本、并发编号、冻结和快照不可变。
- API集成测试：权限、数据范围、幂等、并发冲突、导入错误和审计。
- 前端组件测试：树、矩阵、有效日期切换、脱敏及错误反馈。
- E2E：五条第一阶段UAT全流程。

### 11.2 必过UAT

1. 企业基础数据初始化。
2. 组织未来换上级并按时生效。
3. 成本中心60/40未来变更为70/30。
4. 二次入职恢复原工号且拒绝重叠劳动关系。
5. 编制展示月初、月末、月均和当前人数，超编不阻断招聘。

每条UAT必须同时验证历史、权限、审计和失败路径。

## 12. 交付顺序

### P1-A 配置、组织和主体

先完成字典、组织类型、组织版本、法人、负责人、BP、成本分摊、收入目标及组织管理页面。

### P1-B 人员和雇佣

完成敏感档案、工号、Employment、协议关系、任职、汇报、四类主体、当前及历史查询。

### P1-C 编制、快照和招聘需求

完成职务体系、占编规则、月度编制、冻结、人数统计、快照和招聘需求。

### P1-D 数据治理和整体验收

完成导入导出、敏感访问、审计、outbox、工作台和五条端到端UAT。

每个批次必须在前一批次迁移、测试和文档通过后开始；不允许通过一次超大迁移或单个巨型页面交付。

## 13. 明确不做

- 旧系统切换、双写、持续增量同步和历史重建。
- 候选人、面试、Offer及完整招聘流程。
- 通用审批流程引擎。
- 员工自助、移动端和MCP。
- 考勤、薪酬、社保及税务核算。
- 多租户、多语言、MySQL/Oracle运行时兼容和应用服务器中间件。
- 对万人并发能力作未经压测的承诺。

## 14. 第一阶段完成门槛

第一阶段只有在以下条件全部满足后才可标记完成：

1. P1-A至P1-D所有功能可由PC管理端操作。
2. 当前、未来、历史和快照查询结果相互一致且来源清晰。
3. 关键规则同时具备领域校验和数据库保护。
4. 主管理员、SSC及至少一个受限测试角色通过权限验收。
5. 五条UAT及其失败路径自动化通过。
6. 从空数据库升级、回退测试版本和重新升级均通过。
7. 生产构建、OpenAPI契约、导入模板和操作说明齐全。
8. 代码库、测试、日志和前端产物中不存在真实人员数据或凭据。

第一至三阶段全部完成后，必须生成`docs/review/phase-1-3-implementation-conformance-review.md`，逐项对照需求、设计、数据库、API、管理页面、权限、测试和UAT，标记已实现、部分实现、未实现及其证据，供用户最终Review。
