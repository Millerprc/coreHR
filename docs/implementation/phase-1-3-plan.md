# 业务一至三阶段实施计划

> 状态：`IN_PROGRESS`  
> 日期：2026-08-01  
> 执行分支：`main`（用户明确授权）

## 1. 实施授权与约束

用户已明确授权在尚未提供企业现有数据库表结构的情况下，直接启动业务第一至第三阶段开发。

当前实现遵守以下约束：

- 使用当前已确认的需求、决策和领域规范设计第一版内部数据模型。
- 后续收到现有系统表头、字段和脱敏样例后，通过版本化迁移和导入映射适配，不覆盖历史迁移。
- 未提供的审批流程图、考勤细则和国家本地化规则不得被猜测为正式规则。
- 未确认规则先以可配置结构、明确状态或待验收项承载，不伪造“已完成”业务能力。
- 第一至第四阶段仍以PostgreSQL为唯一运行数据库；MySQL和Oracle支持延后到第五阶段。

## 2. 交付批次

### 批次A：可运行底座与核心数据模型

- FastAPI、React、PostgreSQL、Redis正式工程。
- Alembic迁移基线。
- 一至三阶段核心表及模块注册表。
- 健康检查、统一错误、配置和结构化日志。
- 三阶段管理端导航和建设状态页面。

### 批次B：第一阶段Core HR

- 法人、组织、组织类型、负责人、BP、成本中心和收入目标。
- 职务基础目录、月度编制、人数结果、冻结和快照。
- Person、Employment、工号、主组织、主职务和四类主体。
- 招聘需求、未来生效人事事件、回退、审计、导入导出。

### 批次C：第二阶段流程与人员生命周期

- 流程定义、版本、节点、会签/或签和流程实例。
- 候选人、应聘记录、Offer衔接。
- 入职、转正、调岗、兼岗、借调和离职事件。
- 合同与协议元数据、有效期和变更记录。
- 真实流程图到达前，只交付可配置引擎和明确的示例流程，不固化企业审批链。

### 批次D：第三阶段考勤

- 考勤规则、班次、排班和打卡原始记录。
- 假期类型、请假、销假和审批衔接。
- 考勤日结果、月结果、异常和修订记录。
- 一万人同时在线容量目标在真实场景确认后单独压测，不在首版宣称达成。

## 3. 每批完成定义

每个批次必须同时具备：

1. 数据库迁移。
2. 领域模型和服务端校验。
3. 版本化REST API和OpenAPI契约。
4. 管理端可操作入口。
5. 正常、边界、失败和权限测试。
6. Docker复跑和清理脚本。
7. 交付回执、已知限制和下一批输入清单。

## 4. 当前首批验收

- 干净环境可以启动PostgreSQL、Redis、API和Web。
- Alembic可以从空库升级到最新版本。
- `/health/live`和`/health/ready`工作正常。
- `/api/v1/system/modules`返回一至三阶段模块及建设状态。
- 第一阶段组织、第二阶段流程定义、第三阶段考勤规则各有一个真实数据库API切片。
- React管理端能够展示三个阶段并读取服务端模块状态。
- 后端测试、前端测试和生产构建全部通过。
