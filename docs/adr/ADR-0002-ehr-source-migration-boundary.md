# ADR-0002 EHR 源库镜像与 coreHR 归一化迁移边界

> 状态：Accepted
> 日期：2026-08-08
> 决策人：Miller、Codex
> 关联任务：EHR 真实表结构分析与 coreHR 数据装配

## 背景

现有 EHR 导出包含 114 张 MySQL 表，覆盖核心人事、审批、招聘机器人、考勤结果、认证、内容、分析宽表和薪酬成本。`coreHR` 第一至三阶段使用 PostgreSQL 归一化领域模型，不能把旧系统物理表、旧认证凭据或未确认业务规则直接变成新的运行时事实。

## 决策

- 本地 MySQL `ehr_source` 仅作为源系统结构镜像和迁移分析入口，不成为 `coreHR` 运行时数据库。
- `coreHR` 继续使用 PostgreSQL 作为第一至四阶段唯一业务事实库。
- 源数据通过显式字段映射、枚举转换、有效期重建和外部记录 ID 对照导入现有领域模型。
- 新增数据字典、人员标签和外部记录映射三类结构明确的目标模型。
- 旧认证/会话/2FA、敏感档案明文、薪酬成本、备份表、分析宽表和招聘机器人内部运行表禁止直接灌入 `coreHR`。
- 无法确认语义的字段和表进入待确认或延期清单，不以 JSON 兜底绕过建模决策。

## 备选方案

### 将 114 张 MySQL 表原样复制到 PostgreSQL

- 优点：初期搬运快，字段损失少。
- 缺点：复制旧系统耦合、重复表和安全风险，破坏 `coreHR` 已确认的领域模型。
- 未采用原因：无法形成稳定的产品化数据边界，也不能可靠支持生效日期、版本、审计和后续阶段。

### 让 `coreHR` 运行时同时访问 MySQL 与 PostgreSQL

- 优点：减少首次迁移工作量。
- 缺点：双事实源、事务不一致、权限和部署复杂度显著上升。
- 未采用原因：与当前 PostgreSQL 单一业务库基线冲突，并把实验性源库变成长期运行依赖。

### 把未匹配字段整体放入 JSON

- 优点：实现简单，字段表面上不会丢失。
- 缺点：敏感信息难授权、业务规则不可校验、字段语义和有效期不可治理。
- 未采用原因：只允许已有目标模型明确声明为证据或上下文的 JSON 字段承载受控扩展。

## 影响

- EHR 物理表与 `coreHR` 领域实体之间必须维护逐表、逐字段映射和转换版本。
- 数据迁移必须幂等，并通过外部记录映射保留源系统、源表和源记录 ID。
- 旧系统中的认证秘密、银行账户、证件号码等不得进入日志、测试、提交记录或未授权字段。
- 无生效日期、无稳定主键或仅有显示名称的关系只能作为候选数据，必须校验后才能成为当前结果。
- 第四阶段重新评估薪酬和人力成本表；第五阶段重新评估多数据库运行时兼容性。

## 验证证据

- 本地只读扫描 `ehr_data.sql`：114 张表，97 张存在首条记录，首行字段数解析 0 不匹配，报告未保存原始值。
- DDL-only 提取：114 个 `CREATE TABLE`，不包含 `INSERT`。
- MySQL 8.0.46 隔离库 `ehr_source`：114 张表；97 张表各导入源转储首行，17 张源表为空，共 97 行且单表最多 1 行；原始值仅保留在本机隔离库，不写入报告或中间文件。
- 源报告与 MySQL 目标表名集合 SHA-256：`df236f112e9222c724e08abd7935d97d5c625951a4d2c3962a81fb67a182d171`。
- `coreHR` 新增 4 张归一化衔接表；在独立临时 PostgreSQL 数据库完成全量升级、回退至 `c91a7d225b60`、再次升级。
- `alembic check` 返回 `No new upgrade operations detected`；后端编译通过，自动化测试 `11 passed`。

## 复审条件

- 第五阶段决定让 MySQL 或 Oracle 成为正式运行时数据库。
- 企业确认敏感档案加密、密钥管理和字段级授权方案。
- 需要把招聘机器人、分析仓库或内容系统纳入 `coreHR` 产品边界。
- 第四阶段薪酬模型确认并开始处理人力成本表。
