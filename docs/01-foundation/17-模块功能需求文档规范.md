# coreHR 模块功能需求文档规范

> 文档性质：产品需求拆解与AI开发输入规范
> 状态：`BASELINE / REVIEW_PENDING`
> 版本：v1.3
> 日期：2026-08-19
> 上级文档：[coreHR产品总体PRD](./16-coreHR产品总体PRD.md)

## 1. 目的

本规范用于把产品总体PRD逐级拆成Codex可以直接实施的最小需求和任务，同时让产品决策人能够逐项Review业务规则、系统实现和验收证据。Codex是当前默认开发执行主体；除非产品决策人明确调整，任务不再转交MinimaxCode。

每条需求必须沿以下链路可追踪：

```text
模块 → 能力域 → 功能 → 用户故事 → 业务规则
     → 数据 → 权限 → 接口 → 异常 → 审计 → NFR
     → 验收场景 → 最小开发任务 → 测试与交付证据
```

本规范不替代领域建模、技术设计或测试设计；它规定这些内容在进入开发前至少需要明确到什么程度。

## 2. 适用对象与文档颗粒度

### 2.1 层级定义

| 层级 | 定义 | 示例 |
|---|---|---|
| 产品 | coreHR完整产品 | coreHR |
| 模块 | 可声明依赖和生命周期的产品单元 | Attendance |
| 能力域 | 模块内目标、规则和数据高度相关的一组能力 | 原始打卡 |
| 功能 | 用户或系统可独立触发、观察并验收的结果 | 接收一条原始打卡 |
| 用户故事 | 某类参与者在场景中的目标 | 设备连接器幂等补传打卡 |
| 最小任务 | 一个开发者可在明确文件范围内完成并验证的变更 | 增加打卡幂等唯一约束和API测试 |

### 2.2 一份功能文档只描述一个功能

满足以下任一情况时应拆成不同功能文档：

- 参与者、触发方式或最终业务结果明显不同。
- 可以独立上线、关闭或验收。
- 使用不同权限或审计规则。
- 失败补偿、事务边界或数据所有者不同。
- 一部分仍待确认，而另一部分已经可以开发。

单个页面包含多个按钮不代表只有一个功能；多个页面共同完成一个不可分割的业务结果，也不必机械拆开。

## 5. 状态模型

### 5.1 功能需求状态

```text
DRAFT
  ├→ NEEDS_INPUT → DRAFT
  └→ IN_REVIEW → APPROVED → READY_FOR_TASKS
                              ↓
                         IN_DEVELOPMENT
                         ┌────┴────┐
                         ↓         ↓
              IMPLEMENTED_GENERIC  READY_FOR_UAT → ACCEPTED
                         │
               补齐输入并重新IN_REVIEW
                         └────────→ READY_FOR_UAT

任意未完成状态 → DEFERRED
ACCEPTED → SUPERSEDED / RETIRED
```

| 状态 | 含义 |
|---|---|
| `DRAFT` | 正在整理，不能生成正式开发任务 |
| `NEEDS_INPUT` | 缺少会改变实现或验收结果的业务资料 |
| `IN_REVIEW` | 内容已齐，等待产品/业务评审 |
| `APPROVED` | 业务边界和验收结果已由决策人批准 |
| `READY_FOR_TASKS` | 已通过开发准备检查，可以拆最小任务 |
| `IN_DEVELOPMENT` | 存在正在执行的开发任务 |
| `IMPLEMENTED_GENERIC` | 通用工程实现存在，但企业规则或普通角色UAT未完成 |
| `READY_FOR_UAT` | 实现、测试和环境证据齐全，等待业务验收 |
| `ACCEPTED` | 产品决策人完成业务验收 |
| `DEFERRED` | 已明确延期，记录原因和重新评估条件 |
| `SUPERSEDED` | 被新需求替代，保留引用关系 |
| `RETIRED` | 功能退出使用，数据保留和迁移已经完成 |

不允许从`DRAFT`直接标记`IN_DEVELOPMENT`，也不允许以自动化测试通过代替`ACCEPTED`。
`IMPLEMENTED_GENERIC`补齐企业输入后需要重新进入Review并满足`READY_FOR_UAT`门槛，不能自动跳到`ACCEPTED`。

### 5.2 单条规则状态

每条业务规则、数据、权限、接口、异常、审计和NFR要求只能使用：

- `CONFIRMED`：已经批准，可进入验收。
- `PENDING`：需要输入，不能被开发者猜测。
- `DEFERRED`：不在本功能当前交付范围。
- `NOT_APPLICABLE`：经评审确认不适用，并写明原因。

`IMPLEMENTED_GENERIC`是功能实现状态，不是业务规则确认状态。

### 5.3 任务状态

```text
BLOCKED → READY → IN_PROGRESS → IN_REVIEW → VERIFIED → DELIVERED
```

- `BLOCKED`必须写明缺失输入或依赖任务。
- `VERIFIED`表示自动化和确定性检查通过。
- `DELIVERED`表示代码、迁移、文档和证据齐全，不自动表示业务`ACCEPTED`。

## 6. 进入开发前的准备门槛

功能只有同时满足以下条件，才能标记`READY_FOR_TASKS`：

1. 用户、目标、触发条件、前置条件和最终结果明确。
2. 范围内和范围外边界明确。
3. 会影响结果的业务规则全部为`CONFIRMED`。
4. 数据所有者、稳定标识、有效日期、历史和删除策略明确。
5. 功能、动作、数据范围、字段和高风险权限明确。
6. 同步接口、异步事件、幂等和事务边界明确。
7. 异常、并发、重试、补偿和回退结果明确。
8. 审计字段、敏感信息和保留要求明确。
9. NFR可以量化或明确标记为专项验收。
10. 至少存在正常、边界、失败和权限拒绝验收场景。
11. 对已有数据和接口的迁移、兼容与回滚影响明确。
12. 不存在会让开发者选择不同业务结果的`PENDING`问题。

资料缺失只阻塞受影响的功能或规则，不应阻塞无关功能。

## 8. 业务规则写作要求

### 8.1 合格规则

合格规则必须明确：

- 适用对象和时间点。
- 条件、计算或唯一性维度。
- 成功结果和拒绝结果。
- 配置项的默认值及生效方式。
- 是否影响历史、快照和下游。

示例：

> 同一`source + source_record_id`只能对应一条原始打卡；重复提交且内容一致时返回原记录，内容不一致时返回`PUNCH_IDEMPOTENCY_CONFLICT`，不得覆盖原记录。

### 8.2 不合格规则

以下表述不能直接进入开发：

- “按实际情况处理”。
- “支持灵活配置”，但未说明配置对象、范围和默认值。
- “性能要快”或“支持高并发”。
- “权限和现有系统一致”。
- “失败后重试”，但未说明幂等和最终状态。
- “可以回退”，但未说明后续事件、下游同步和历史保留。

## 9. 数据与接口写作要求

### 9.1 数据

- 先写业务含义和唯一性，再写数据库字段。
- 日期需要区分业务日期、带时区时间和系统记录时间。
- 金额必须同时说明币种、精度和舍入。
- 有效日期数据必须说明区间重叠、未来生效和更正规则。
- 开放JSON只能用于已评审的扩展字段，不能规避敏感字段和数据模型Review。

### 9.2 接口

- 明确调用者、所有者、认证、权限和数据范围。
- 写明同步事务边界和异步最终一致性边界。
- 创建、回调、导入和任务触发接口明确幂等键。
- 批量接口明确整批失败或部分成功、行级错误和重复执行结果。
- 外部依赖失败时明确本地事务是否提交及如何补偿。

## 10. 验收场景最小集合

每个功能至少包含：

1. 一条最常用成功路径。
2. 一条业务边界值。
3. 一条业务规则拒绝路径。
4. 一条无权限或越权路径。
5. 一条重复请求或并发冲突路径。
6. 一条审计证据核对路径。

涉及后台任务、外部系统、敏感数据、有效日期或回退时，还要分别增加：

- 任务中断后安全重试。
- 下游失败和人工补偿。
- 明文访问和导出拒绝。
- 生效日前、生效日和历史时点查询。
- 存在后续事件时的回退拒绝或补偿结果。

计算类功能必须使用明确的输入—期望输出样例，仅提供制度文字不能视为计算验收完成。

## 11. 最小开发任务规范

### 11.1 拆分原则

一个最小任务应当：

- 只产生一个明确且可验收的结果。
- 可以在不猜业务规则的情况下完成。
- 声明文件或模块所有权，避免并行修改冲突。
- 包含实现、迁移、测试和相关文档更新，不把验证留给下一任务。
- 尽量可以独立回滚；不可逆变化写清恢复路径。
- 通常在一个连续开发周期内完成；如果任务内仍有多个独立结果，应继续拆分。

不要为追求“原子化”把同一个约束的数据库迁移、领域校验和测试拆给互不知情的任务。

## 12. 功能完成定义

### 12.1 工程实现完成

标记`READY_FOR_UAT`前必须满足：

- 所有范围内任务均为`VERIFIED`或`DELIVERED`。
- 代码符合模块依赖和数据所有权规则。
- 每项需求驱动的代码变化均能从规则落点的追踪注释回到稳定需求或决策ID。
- 数据库迁移可在空库和现有版本升级路径执行。
- 正常、异常、权限、并发、幂等和审计自动化测试通过。
- 页面、API、任务和错误码与需求文档一致。
- 前端页面符合批准的Ant Design规范与`MODAL`/`DRAWER`/`NEW_TAB`载体，宿主页上下文没有被当前标签页导航替换。
- 所有范围内前端页面均有`PROTOTYPE_APPROVED`记录，代码实现与批准的Pencil画板版本一致。
- 日志、指标、健康检查和补偿入口可用。
- 安装、升级、备份恢复或发布手册已经同步。
- 未实现内容不会显示为可用入口，也没有用假数据伪装完成。

### 12.2 业务验收完成

标记`ACCEPTED`前还必须满足：

- 产品决策人使用批准的场景完成UAT。
- 企业字段、流程、计算规则和权限不存在影响范围内的`PENDING`项。
- 页面结果、导出、接口、快照和审计可以对账。
- 对应部署环境的安全、容量和恢复要求通过。
- Review记录包含批准版本、验收人、日期和遗留项处置。

### 12.3 不等价关系

- 代码存在不等于功能完成。
- 主管理员能够演示不等于普通角色权限通过。
- 通用算法存在不等于企业计算规则确认。
- 单元测试通过不等于跨模块链路验收。
- AI对抗验证不等于确定性测试和人工UAT。
- 某硬件上短时压测通过不等于所有规模部署均受支持。

## 13. 变更控制

- 已批准业务规则发生变化时，先更新功能文档和版本，再修改任务或代码。
- 新需求或需求变更引起代码变化时，同步新增、更新或删除对应需求追踪注释，避免注释继续描述旧规则。
- 影响既有数据、接口或审计解释的变更必须记录迁移和兼容策略。
- 被新功能替代时，将旧文档标记`SUPERSEDED`并链接新功能，不删除历史。
- 紧急修复可以先止损，但交付前必须补齐需求ID、规则、测试和Review记录。
- 发现实现与文档不一致时，不默认以代码为准；由产品决策人确认修正文档还是修正实现。

## 14. AI开发约束

Codex执行开发任务时必须遵守：

- 不推断`PENDING`规则，不把推荐值写成用户确认。
- 不扩大文件所有权，不顺手重构无关模块。
- 不以开放JSON、硬编码或管理员通配权限绕过未完成设计。
- 不修改其他模块拥有的数据表，使用公开应用服务或事件合同。
- 不降低审计、权限、敏感数据和历史保留底线。
- 工具或测试失败时如实记录，不用模拟输出充当证据。
- 回执必须引用功能、规则、验收场景和实际修改文件。
- 不得遗漏需求追踪注释，也不得用无需求ID的泛化注释伪装合规。

## 15. 文档Review检查表

评审人逐项回答“是/否/不适用”：

1. 文档是否只描述一个可独立验收的功能？
2. 是否能明确说出谁在什么条件下得到什么结果？
3. 是否区分确认规则、待确认问题和推荐方案？
4. 数据所有者、唯一键、有效日期和历史策略是否明确？
5. 权限是否覆盖动作、数据范围、字段和高风险操作？
6. 接口是否明确幂等、事务、版本和失败补偿？
7. 是否覆盖异常、并发、回退、审计和敏感数据？
8. NFR是否可以在指定环境中验证？
9. 验收场景是否包含明确输入、动作和预期证据？
10. 是否可以在不猜业务规则的情况下拆出最小任务？
11. 是否说明对已有数据、模块和部署的影响？
12. 是否存在与父级PRD或已确认决策冲突的内容？
13. 所有需求驱动的代码变化是否明确了追踪注释所引用的ID和预计代码落点？
14. 涉及前端时，是否明确宿主页、`MODAL`/`DRAWER`/`NEW_TAB`载体及其打开、退出和状态恢复行为？
15. 涉及前端时，是否登记Pencil文件、画板ID、版本和`PROTOTYPE_APPROVED`证据？

任一关键项为“否”时，不得进入`READY_FOR_TASKS`。
