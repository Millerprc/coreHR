## 1. 文档目的与权威边界

本文件定义coreHR长期稳定的产品定位、产品分层、模块边界、部署分级、质量门槛和演进原则，是后续模块级需求文档的父级依据。

本文件不展开每个模块的字段、页面、计算公式和流程节点。每项功能必须继续按[模块功能需求文档规范](./17-模块功能需求文档规范.md)形成可评审、可开发、可测试、可验收的子级需求文档。

既有第一至第三阶段需求规格、PRD和领域规范继续保留，作为已确认业务事实、历史阶段基线和子级需求输入；它们不再承担整个产品的总PRD职责。发生冲突时按[正式文档目录](./00-正式文档目录.md)规定的优先级处理。

## 2. 产品定位

coreHR是一套面向不同规模组织的开源、可自托管、产品化人力资源管理系统。它首先解决组织与人员主数据、人员生命周期、考勤和薪酬等HR核心问题，并通过稳定的平台能力和受控扩展点适配不同企业。

“普惠”在本产品中表示：

- 小企业可以用较低的硬件与运维成本使用完整业务能力。
- 企业规模、部署档位和商业服务方式不得成为阉割开源业务功能的理由。
- 同一业务套件在单机和集群拓扑中保持相同业务语义、数据模型和接口契约。
- 产品默认支持私有化和离线环境，不把依赖某一云厂商作为运行前提。
- 安装、升级、备份、恢复和诊断属于产品能力，不是仅供开发者参考的脚本。

coreHR不是通用ERP、通用低代码平台，也不依赖ERPNext，不是Frappe的二次开发版本。Frappe Framework、ERPNext及Frappe HRMS只作为产品分层、应用安装和扩展机制的研究样本。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 提供覆盖HR核心业务的完整、可组合业务套件。
2. 以统一人员、组织、有效日期和事件模型支撑各模块衔接。
3. 让同一套产品从5人组织演进到大型集团，无需为扩容重写核心业务。
4. 以模块化单体作为默认交付形态，保持轻量安装、调试和升级能力。
5. 让身份、文件、消息、任务、监控和外部连接等基础设施可以通过受控适配器替换。
6. 对敏感人事数据提供服务端权限、加密、审计、备份和恢复闭环。
7. 让AI Native Coding产出的需求、代码、测试和交付证据能够双向追踪。

### 3.2 当前非目标

- 不建设可以任意生成业务表和业务规则的通用DocType或无代码平台。
- 不把所有业务模块预先拆成微服务。
- 不允许第三方模块绕过应用服务直接写入其他模块数据表。
- 不以换一个连接字符串的方式宣称兼容MySQL或Oracle。
- 不在完成对应部署和真实压测前宣称支持一万、五万或二十万规模。
- 不以数据库副本替代历史备份和时间点恢复能力。

## 4. 目标用户与产品使用方式

### 4.1 用户角色

| 用户 | 主要目标 | 开放节奏 |
|---|---|---|
| 系统主管理员 | 安装初始化、账号权限、模块配置、异常恢复和安全管理 | 首批 |
| SSC及HR系统管理员 | 组织、人事、流程、考勤、薪酬等集中运营 | 首批，按模块开放 |
| HRBP及专业BP | 按服务范围查看和办理业务 | 企业规则确认后开放 |
| 业务负责人 | 查看下级组织并处理授权业务 | 流程和数据范围确认后开放 |
| 员工 | 自助查询、申请、修改和移动服务 | ESS套件实施后开放 |
| 审计与合规角色 | 只读核查业务结果、操作与敏感访问 | 权限模型验收后开放 |
| 外部系统 | 通过版本化API、事件或连接器交换数据 | 接口合同确认后开放 |

角色名称不等于固定权限。除紧急启动所需的主管理员外，功能、动作、数据范围和字段权限均通过授权策略组合。

### 4.2 产品交付原则

- 业务套件决定企业启用哪些业务能力。
- 部署档位决定容量、可用性、恢复能力和运维复杂度。
- 企业人数仅作为选型参考，不作为功能开关或许可限制。
- 实际选型还必须评估在线人数、峰值请求、批处理窗口、历史数据量、附件量、安全等级及RPO/RTO。

### 4.3 Web设计与页面载体

- 所有Web前端设计遵循Ant Design官方当前稳定版的设计原则、组件模式和可访问性要求；实际编码只使用仓库锁定版本已经支持的API。
- 列表、组织树、仪表盘和工作台是保留上下文的宿主页。从宿主页进入新增、编辑、详情、流程或子任务时，只能选择弹窗类容器（Modal或Drawer）或新的浏览器标签页，不在当前标签页替换宿主页。
- 简短确认和轻量表单默认使用Modal；需要保留宿主页上下文的中等复杂编辑或预览默认使用Drawer；多分区、长表单、历史对比、完整流程和需要并行参照的任务默认打开具有稳定URL的新浏览器标签页。
- 每份功能需求必须明确页面载体、打开和关闭行为、未保存变更处理、权限拒绝、加载与失败状态，不能留给开发人员临时决定。
- 所有新增或变更的前端页面必须在编码前完成Pencil原型并由产品决策人确认；功能需求登记具体源文件、画板ID和版本，未达到`PROTOTYPE_APPROVED`不得进入前端开发。
- Moka、Frappe等外部系统的页面和截图只作为研究输入。coreHR提炼业务目标与交互规律后形成自己的信息架构、视觉表达和实现，不复制其代码、品牌资产或页面成品。

详细执行标准见[Ant Design页面与交互载体规范](../design/antd-page-interaction-standard.md)。

## 5. 总体产品架构

```text
PC管理端 / 员工门户 / Mobile / MCP / 外部API
                         │
                    接口与体验层
                         │
                  模块依赖DAG
 Workforce Core ─────────────────────→ Kernel
 Workflow ───────────────────────────→ Kernel
 Recruitment / Contract / Attendance → Kernel + Workforce Core
 Payroll ────────────────────────────→ Kernel + Workforce Core + Attendance
 ESS ────────────────────────────────→ Kernel + Workforce Core + 已启用套件
 Integration ────────────────────────→ Kernel + 目标套件公开合同
 （Recruitment / Contract / Attendance / Payroll可选依赖Workflow）
                         │
              Platform Kernel（必装）
       身份权限 / 配置字典 / 审计 / 任务 / Outbox
       模块注册 / 迁移 / 文件端口 / 消息端口 / 观测
                         │
                  基础设施适配层
       PostgreSQL / Redis / 对象存储 / 消息服务
          密钥服务 / 监控平台 / 外部身份与系统
```

Platform Kernel是业务套件共同依赖的轻量平台内核，不是传统意义上仅位于应用与数据库之间的数据库中间件，也不是一个新的通用ERP底座。

### 5.1 Platform Kernel职责

Platform Kernel只承载跨业务套件稳定复用的能力：

- 用户、身份提供方、会话和租户上下文预留。
- 角色、动作、数据范围、字段权限及默认拒绝策略。
- 系统配置、数据字典、稳定编码和功能能力注册。
- 结构化审计、敏感访问日志、Trace ID和统一错误合同。
- 幂等、后台任务、调度、Outbox和可重试执行框架。
- 模块清单、依赖检查、启停状态、版本和迁移编排。
- 文件、对象存储、消息通知、密钥和外部集成端口。
- 健康检查、日志、指标和追踪输出端口。

### 5.2 Platform Kernel禁止承载

- 组织有效期、单父树和合并拆分规则。
- Person、Employment和劳动关系唯一性规则。
- 编制、招聘、人事流程、合同和协议规则。
- 考勤、假期、薪酬、社保和税务计算。
- 为某一客户写死的字段、审批人、接口映射和统计口径。

这些规则分别属于Workforce Core或对应业务套件。

### 5.3 Workforce Core职责

Workforce Core是coreHR产品发行的必装业务事实底座，也是所有使用人员、组织或雇佣事实的业务套件的必需依赖，负责：

- Person永久自然人身份及多次Employment。
- 法人、业务组织、虚拟关系、职务与人员关系。
- 主组织、主职务、汇报、负责人、BP和主体关系。
- 当前结果、有效期历史、快照和人事事件。
- 工号、稳定业务标识和主数据质量约束。
- 向依赖Workforce Core的业务套件和目标连接器提供稳定查询及命令接口。

业务套件不得复制Workforce Core中的人员或组织主档。

## 6. 业务套件边界

| 套件 | 核心责任 | 主要依赖 | 不承担 |
|---|---|---|---|
| Recruitment | 招聘需求、候选人、应聘、Offer及录用转换 | Kernel、Workforce Core，可选Workflow | 编制强制控制、入职生效 |
| Workflow | 受控流程定义、版本、实例、任务、会签/或签和条件选路 | Kernel；通过领域命令调用业务套件 | 任意脚本、SQL节点、直接改业务表 |
| Contract | 劳动合同和其他协议的版本、续签、变更、解除与提醒 | Kernel、Workforce Core，可选Workflow | 电子签章平台本身 |
| Attendance | 规则、班次、排班、打卡证据、假勤、日报月报和冻结 | Kernel、Workforce Core，可选Workflow | 薪酬扣款和工资计算 |
| Payroll | 薪酬、社保、税务、发薪流程和费用分摊 | Kernel、Workforce Core、Attendance，可选Workflow | 人员主档和考勤证据采集 |
| ESS | 员工本人查询、申请、资料维护和移动体验 | Kernel、Workforce Core及启用的业务套件 | 绕过业务权限直接修改事实数据 |
| Integration | 企业微信、OA、财务、设备及其他下游连接器 | Kernel和被集成套件的公开合同 | 把客户映射写入核心领域模型 |

套件边界描述的是产品责任，不要求当前立即拆成独立进程。默认在同一代码仓库和模块化单体内交付。

## 7. 模块生命周期与依赖规则

### 7.1 模块清单

每个模块必须声明：

- 稳定模块代码、名称、版本和责任边界。
- 必需依赖、可选依赖和最低兼容版本。
- 提供的能力、使用的能力和公开接口。
- 配置项、权限代码、后台任务和健康检查。
- 数据所有权、迁移序列和回滚限制。
- 启用、停用和升级时的业务行为。

### 7.2 依赖方向

```text
Workforce Core                            → Platform Kernel
Workflow                                  → Platform Kernel
Recruitment / Contract / Attendance       → Platform Kernel + Workforce Core
Payroll                                   → Platform Kernel + Workforce Core + Attendance
ESS                                       → Platform Kernel + Workforce Core + 已启用套件
Integration                               → Platform Kernel + 目标套件公开合同
Recruitment / Contract / Attendance / Payroll ──可选→ Workflow
```

- Platform Kernel是所有模块的直接技术底座，不得反向依赖HR业务套件。
- coreHR产品的最小正式组合是Platform Kernel + Workforce Core；两者均为产品必装项。
- 从代码依赖看，Workforce Core和通用Workflow均直接依赖Platform Kernel，二者互不形成强制依赖；这不表示coreHR可以在缺少Workforce Core时作为HR产品交付。
- Recruitment、Contract和Attendance依赖Platform Kernel及Workforce Core，可选依赖Workflow。
- Payroll按当前基线依赖Platform Kernel、Workforce Core和Attendance，可选依赖Workflow。
- ESS依赖Platform Kernel、Workforce Core及实际启用的业务套件。
- Integration依赖Platform Kernel，并按目标连接器声明对相应业务套件公开合同的依赖。
- Workforce Core不得依赖Recruitment、Attendance或Payroll等可选套件。
- 业务套件之间优先使用公开应用服务或版本化事件合同。
- 跨模块读取必须通过公开查询接口、只读投影或明确批准的共享事实，不得任意联表形成隐式依赖。
- 跨模块写入只能调用数据所有者提供的命令接口。
- 检测到依赖缺失、版本不兼容或迁移失败时默认拒绝启用。

### 7.3 生命周期状态

```text
registered → installed → enabled → disabled
                    └→ upgrading → enabled / failed
```

- “停用”默认阻止新业务操作，但保留历史读取、审计和导出能力。
- 已产生业务数据的模块不得通过普通卸载物理删除数据。
- 模块升级必须先检查依赖、迁移、备份和回滚条件。
- 当前不建设第三方任意代码热加载、插件市场或运行时脚本机制；受控模块注册和适配器接口已经足够。

## 8. 部署分级与规模参考

五档部署使用同一套产品代码和业务功能。下表人数不是容量承诺，而是启动选型参考。

| 档位 | 人员规模参考 | 推荐部署形态 | 最低恢复要求 |
|---|---:|---|---|
| 便携单机版 | 5～100 | 单机容器化运行API、任务、PostgreSQL和Redis；本地或对象文件存储 | 异机或异地加密备份，可执行恢复 |
| 标准生产版 | 100～1,000 | 单机多进程/多容器，独立后台任务、监控告警和对象存储；可选温备机 | 定期基础备份、持续增量日志、恢复演练 |
| 企业版 | 1,000～10,000 | 多API节点，独立数据库主备、Redis和对象存储，负载均衡和受控故障切换 | 数据库副本、时间点恢复、异地备份 |
| 集团版 | 10,000～50,000 | API与任务集群、只读副本、数据分区、集中观测，按证据拆分报表或热点任务 | 跨故障域部署、明确RPO/RTO和演练 |
| 超大型架构目标（未验证） | 50,000～200,000+ | 多可用区、热点接入/计算服务、分布式任务、OLTP与分析负载隔离、异地灾备 | 多层备份、受控切换、持续容量和灾备验证 |

“超大型架构目标”是用于指导接口、数据和运行边界的演进档位，不是当前发行版的容量声明。

### 8.1 选型输入

部署选型必须至少输入：

- 总人员数、同时在线人数和会话持续时间。
- 普通查询、批量写入、集中打卡和薪酬查询的峰值RPS。
- 打卡峰值集中窗口、考勤和薪酬批处理完成窗口。
- 历史年限、每日事件量、附件容量和增长率。
- 可接受停机时间、可接受数据丢失量及监管要求。

### 8.2 容量声明规则

- 当前8GB环境只用于功能开发和业务验收，不构成万人容量证明。
- “架构可演进到二十万级”不等于“当前已支持二十万”。
- 任何规模声明必须绑定硬件拓扑、数据规模、请求模型、软件版本、测试时长、P95/P99、错误率和任务积压结果。
- 二十万级需要针对集中打卡、考勤重算、薪酬集中查询、大型组织权限和多年审计数据分别验证。
- 未通过目标档位的完整压测、故障和恢复测试时，只能标记为“架构目标”，不能标记为“已支持”。

## 9. 轻量与可扩展原则

### 9.1 默认模块化单体

coreHR默认以模块化单体交付：

- 一个版本、一套业务语义和统一发布流程。
- API进程保持无状态，可在需要时增加实例。
- 批量导入、快照、考勤和薪酬等长任务通过可重试后台任务执行。
- Redis不保存不可重建的业务事实。
- Outbox确保业务提交和后续事件发布之间可追溯。

### 9.2 服务拆分触发条件

只有满足至少一种证据时才拆分独立服务：

- 目标负载下已定位到独立热点，单体水平扩展不能经济解决。
- 该能力需要独立故障域、扩缩容或发布节奏。
- 数据一致性和所有权边界已经明确，拆分收益高于分布式复杂度。
- 安全、监管或地域要求必须物理隔离。

优先候选通常是打卡接入、考勤计算、薪酬批处理、报表分析和外部集成；组织、人员、有效日期等核心事务默认保持统一。

### 9.3 可插拔范围

允许通过稳定端口替换：

- 身份：本地账号、企业微信、OIDC、LDAP。
- 文件：本地受控存储、S3、MinIO或兼容对象存储。
- 通知：站内、邮件、企业微信、短信、自建OA。
- 任务：本机任务进程或经验证的外部任务队列。
- 监控：本地结构化日志、Prometheus或企业监控平台。
- 密钥：本地密钥文件、云密钥服务或企业密钥平台。
- 集成：Webhook、版本化API和特定系统连接器。

Apusic、独立API网关、消息总线和ESB等企业级中间件在第五阶段按国产化、集成规模和部署要求评估。它们不得成为便携版和标准版的强制依赖，也不因引入其中一项而默认改变业务数据库或核心业务模型。

不允许通过插件改变人员唯一性、有效日期、权限底线、审计不可篡改要求或核心事务边界。

## 10. 数据架构

### 10.1 数据事实

核心业务需要区分并关联：

1. 当前有效结果。
2. 带生效区间的历史版本。
3. 产生变化的业务事件或更正记录。
4. 月初、月末或业务时点快照。
5. 操作审计和敏感访问记录。

任何一层均不能独立替代其他层。业务主数据默认不物理删除。

### 10.2 数据所有权

- 每张业务表只能由一个模块拥有。
- 数据所有者负责写入规则、数据库约束、迁移和兼容策略。
- 其他模块通过稳定ID、公开查询或事件引用数据。
- 大表从设计时保留日期、主体、组织等可检索维度；是否分区由数据量和查询证据决定。
- 报表和分析负载在集团版以上可与事务库隔离，但不得形成不可追溯的第二事实源。

### 10.3 数据库支持边界

- PostgreSQL是当前唯一开发、测试和生产业务数据库基线。
- Repository边界用于保护领域与持久化细节，不代表已经实现跨数据库兼容。
- MySQL和Oracle属于第五阶段的适配目标，需要分别完成驱动、SQL方言、标识生成、时间、JSON、索引、约束、锁、分页、迁移、备份恢复和性能测试。
- 未建立对应迁移和自动化测试矩阵前，不得宣传支持MySQL或Oracle。

## 11. API、事件与外部集成

- 对外业务API使用版本化命名空间和稳定错误码。
- 创建、批量导入、事件执行和外部回调支持幂等。
- 接口执行服务端认证、动作、数据范围和字段权限校验。
- 外部系统不得直连业务数据库修改数据。
- 事件合同包含稳定事件代码、对象ID、发生时间、版本和幂等标识。
- 合同变更遵循兼容期和废弃策略，不无通知破坏现有连接器。
- 下游失败不回滚已经提交的本地业务事实，通过Outbox、重试和人工补偿闭环处理。
- MCP是受控业务API的入口适配器，不直接访问数据库或绕过权限。

## 12. 安全、隐私与审计

- 所有生产入口默认鉴权，未知角色、权限、数据范围和办理人表达式默认拒绝。
- 权限至少覆盖功能、动作、数据范围、字段和高风险操作。
- 证件、银行账户、薪资等敏感字段按分级加密、脱敏和授权访问。
- 明文查看、导出、权限变更、解冻、回退和数据修订写入不可由普通业务管理员修改的审计记录。
- 密钥和生产凭据不进入代码、镜像、日志、示例数据或交付文档。
- 非生产环境只使用合成或脱敏数据。
- coreHR默认不要求把企业业务数据上传至项目维护者或公共云；启用外部存储、监控或AI服务时，必须由部署方显式配置并评估数据边界。
- 模块和适配器不得通过开放JSON长期承载未经评审的敏感字段。

## 13. 可观测、任务与运行保障

### 13.1 可观测性

所有部署档位至少提供：

- 结构化日志、统一Trace ID和稳定错误码。
- API请求量、延迟、错误率和资源使用情况。
- 数据库连接、慢查询、复制和存储空间观测。
- 导入、生效、快照、考勤、薪酬和集成任务的状态及积压。
- 备份结果、恢复校验和关键任务失败告警。

### 13.2 后台任务

- 任务必须可识别、可重试、可查询、可告警和可人工补偿。
- 同一业务任务重复执行不得产生重复业务结果。
- 任务状态不能只保存在进程内存或Redis。
- 长任务限制并发、分批执行，并保存输入版本和结果证据。
- 调度器多实例运行时必须避免同一计划任务被重复生效。

## 14. 备份、灾备与高可用

- 单机生产也必须具备异机或异地备份，备份不得只放在主服务器同一磁盘。
- 数据库副本用于提高可用性，基础备份和增量日志用于抵抗误删、损坏及按时间点恢复，两者必须同时规划。
- Redis缓存丢失后必须能够重建，不得成为唯一事实源。
- 数据库、附件、配置和密钥分别定义备份、保留和恢复步骤。
- 定时执行的是备份、校验和恢复演练；主备复制在需要时持续运行。
- 双节点缺少可靠仲裁时默认采用人工确认或受控切换，避免双主写入。
- 每个生产项目在上线前冻结RPO、RTO、备份保留、切换方式和责任人，并通过实际恢复演练验证。

## 15. 安装、升级与回滚

所有正式发行至少提供：

- 明确支持的操作系统、CPU架构、容器运行时和依赖版本。
- 开发、体验、生产和离线安装配置边界。
- 首次管理员、安全密钥、域名和HTTPS初始化流程。
- 版本化数据库迁移、迁移预检和失败停止机制。
- 升级前备份、兼容性检查、升级证据和回滚说明。
- 备份、恢复、诊断和健康检查入口。
- 发布说明、破坏性变更说明和支持版本窗口。

业务数据迁移已经执行且不可逆时，不得用“回滚应用镜像”冒充完整回滚；必须明确恢复备份或前向修复路径。

## 16. 非功能质量门槛

### 16.1 通用门槛

- 正确性：核心业务约束同时具备领域校验、数据库约束或可证明的等效保护。
- 安全性：通过越权、敏感字段、导出、会话、秘密和高风险操作测试。
- 可追溯：需求、规则、代码、迁移、测试、UAT和交付证据能够互相引用。
- 可恢复：备份能够在隔离环境恢复，任务和接口能够幂等重试。
- 可升级：支持版本化迁移，依赖不兼容和预检失败时安全停止。
- 可运维：故障可以通过日志、指标、Trace ID和任务记录定位。
- 可移植：核心业务不依赖某个云厂商专有服务才能运行。

### 16.2 容量门槛

每档性能验收必须使用目标部署拓扑和接近真实的数据分布，至少记录：

- 目标会话数和分场景请求模型。
- 持续负载、峰值负载和测试持续时间。
- P50、P95、P99、错误率和超时率。
- 数据库、缓存、任务队列和系统资源峰值。
- 高峰结束后的任务积压清空时间。
- 节点故障、数据库切换和恢复后的数据一致性。

人数、单个QPS或“页面能打开”均不能单独作为容量验收结论。

## 17. 阶段路线与产品架构映射

| 阶段 | 主要产品交付 | 架构落点 |

| 第一阶段 | 组织、法人、职务、人员、编制、招聘需求和主数据 | Workforce Core及Recruitment起点 |

## 18. 产品级发布与完成定义

一个业务套件只有同时满足以下条件，才能声明为正式可用：

1. 模块能力域和功能需求文档已经批准，未决问题不影响目标路径。
2. 与Kernel、Workforce Core及其他套件的依赖和数据所有权明确。
3. 正常、边界、异常、并发、权限、幂等、回退和审计场景通过。
4. 数据迁移、初始化、升级、备份和恢复路径可重复执行。
5. 页面、API、任务、日志和运维文档与实际实现一致。
6. 对应部署档位的资源、容量和恢复门槛经过验证。
7. 产品决策人完成业务UAT和规则确认。

开源发布、工程实现、企业规则UAT和规模压测是不同状态，不得互相替代。

## 19. 后续需求文档产出方式

后续采用以下逐级拆分：

```text
产品总体PRD
  → 模块
    → 能力域
      → 功能
        → 用户故事与业务规则
          → 数据/权限/接口/异常/审计/NFR
            → 验收场景
              → 最小开发任务
```

每份功能需求只描述一个可独立验收的功能；跨模块规则通过依赖和接口引用，不复制粘贴形成多个事实来源。具体模板、编号、状态和完成定义见[模块功能需求文档规范](./17-模块功能需求文档规范.md)。

### 19.1 当前开发执行方式

- 产品决策人负责确认需求边界、业务规则、优先级和最终UAT。
- Codex是当前默认开发执行主体，直接负责需求拆解、技术设计、代码、迁移、测试、复审和交付回执。
- 后续任务不再转交MinimaxCode；除非产品决策人再次明确调整执行主体。
- 历史MinimaxCode任务基线和交付记录继续作为既有实现证据保留，不代表后续开发责任。
- 自主开发不降低Review要求；涉及代码变更时仍需执行独立代码复审、安全检查和与风险相称的验证。
- 新需求或需求变更引起代码变化时，必须在实际规则落点写需求追踪注释，引用稳定需求或决策ID并说明变更原因。
