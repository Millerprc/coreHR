# HRIS 第一阶段需求规格

> 状态：`PARTIAL`  
> 版本：v0.1-draft  
> 读者：产品决策人、业务分析、架构设计、开发与测试  
> 注意：本文件尚未达到开发批准状态

## 1. 阶段目标

建立 HRIS 的组织与人员基础数据底座，使 HR 系统管理员和SSC能够：

- 初始化并持续维护企业基础数据。
- 查询当前有效的组织、主体、职务、编制和人员结果。
- 按生效日期维护主数据关系。
- 保留历史版本、月初月末快照和操作记录。
- 创建与跟踪招聘需求。
- 为第二阶段流程驱动的入转调离提供稳定主数据。

## 2. 领域边界

### 2.1 纳入范围

| 领域 | 第一阶段能力 |
|---|---|
| 系统基础 | 登录、账号、角色权限底座、字典、编码、审计、附件、导入导出 |
| 法人主体 | 独立主体档案、与组织关系、生效区间 |
| 组织 | 单父业务组织树、可配置组织类型、负责人、虚拟组织与成员关系 |
| 成本中心 | 成本中心档案、组织分摊比例、生效日期和版本 |
| 收入目标 | 叶子组织年度/月度目标、币种、版本、按币种向上汇总 |
| 职务 | 职务及其与职级、职等、职类、序列关系；详细字段待现有表结构 |
| 编制 | 按组织+职务+年月维护编制数，展示人员结果和差额 |
| 招聘需求 | 需求创建、状态跟踪、与组织/职务的弱关联 |
| 自然人 | 永久人员身份、证件、联系方式等基础资料 |
| 雇佣关系 | 每次雇佣独立记录，二次入职复用自然人和工号 |
| 人事数据 | 当前结果维护、有效期、变更日志、快照及事件衔接 |

### 2.2 不纳入范围

- 候选人、面试、Offer及招聘门户。
- 通用流程引擎。
- 完整入转调离流程。
- 合同协议管理。
- 员工自助修改资料。
- 考勤、请假、薪酬、社保、个税。
- 编制阻断招聘或自动预留。
- 未来日期组织树预览。
- 多租户和完整多语言。

## 3. 核心概念

### 3.1 自然人与雇佣

采用分层模型：

```text
Person（自然人，永久）
└─ Employment（一次雇佣经历）
   ├─ Employee No（六位纯数字，二次入职复用）
   ├─ 组织与职务关系
   ├─ 劳动合同主体
   ├─ 发薪主体
   ├─ 社保主体
   └─ 个税申报主体
```

规则：

- 同一自然人可以有多次历史雇佣记录。
- 二次入职恢复原工号。
- 同一雇佣关系在同一生效日期，四类主体各自只能有一个有效值。
- 四类主体默认相同，但管理员可以分别调整。
- 自然人匹配优先使用可靠证件，无法自动匹配时允许SSC人工确认。

同一自然人同一有效期间只能有一条法人劳动关系；历史劳动关系可以有多条但有效期不得重叠。
合作、劳务派遣等协议关系可以同时存在，不计为第二条法人劳动关系。

### 3.2 组织

当前默认组织类型：

- 集团
- BG
- BU
- 部门

规则：

- 组织类型由管理员配置。
- 不限制不同组织类型之间的上下级组合。
- 在业务组织树中，每个组织同一时间只能有一个直接上级。
- 组织编码使用纯流水号自动生成。
- 初始化导入保留历史组织编码，新编码自动避让冲突。
- 组织改名、换上级、合并、拆分、撤销支持未来生效。
- 产品仅展示当前有效组织树；未来变更在组织详情中按生效日期查看版本、事件和快照信息。

### 3.3 虚拟组织及BP

- 实线组织表示业务组织关系。
- 虚线组织用于委员会、BP等兼岗或专业组织关系。
- BP类型包含HRBP、EBP、TBP、FBP。
- 同一个人在同一有效期间只能兼一种BP类型。
- 一个BP可以服务多个业务组织。
- 一个业务组织可以被多个不同BP服务。
- BP服务关系不改变员工主组织和主职务。

### 3.4 负责人

- 每个组织最多三名负责人。
- 三人均为主负责人，不设置第一负责人或副负责人。
- 流程中可能使用会签或或签，不以负责人排序决定。

### 3.5 法人及四类主体

法人作为独立主数据，不等同于组织：

- 一个BU可能关联多个法人。
- 一个法人可能关联多个组织。
- 员工的劳动合同、发薪、社保、个税申报主体分别保存。
- 基础主体关系允许按生效日期直接维护。
- 员工主体变化在第二阶段通过人事事件驱动；第一阶段保留事件接口和审计能力。
- 同一自然人同一有效期间只能有一条法人劳动关系。
- 合作、劳务派遣等其他关系作为协议关系独立保存，可以与劳动关系并存。

### 3.6 成本中心

- 一个组织可以分摊到多个成本中心。
- 多个组织可以归集到同一成本中心。
- 同一组织同一有效期间的分摊比例合计必须为100%。
- 分摊关系具有生效日期、失效日期和版本。
- 第一阶段只实现组织级分摊，数据模型不得阻碍未来员工级覆盖。

### 3.7 职务与编制

- 当前编制维度为组织+职务+年月。
- 职务、职级、职等、职类、序列的字段和关系以后续真实表结构为准。
- 正式员工和员工类型为“校招生”的人员占编。
- 其他人员类型当前不占编，但占编规则必须可配置。
- 创建待入职档案并明确待入职日期后，进入相关统计。

编制只用于台账与结果展示：

- 不阻断招聘。
- 不预留招聘名额。
- 不要求招聘需求必须有空编。
- 招聘需求只弱关联组织、职务及编制数据。

### 3.8 编制指标

已确认指标口径如下：

| 指标 | 来源 |
|---|---|
| 月度编制数 | 管理员按组织+职务+年月维护 |
| 月初人数 | 月初系统快照 |
| 月末人数 | 月末系统快照 |
| 月均人数 | `(月初人数 + 月末人数) / 2` |
| 当前人数 | 当前有效雇佣及占编规则实时计算 |
| 编制差额 | 月度编制数 - 当前人数 |

年度页面展示当前月份的编制和人员结果，不将12个月人数相加。

### 3.9 冻结

系统需要区分：

- 业务冻结：特殊时期对编制数据进行业务限制。
- 月结冻结：月结后限制历史月份数据变更。

业务冻结范围由年月、组织、职务三个维度任意组合，未选择的维度表示该维度全部范围。命中冻结范围后：

- 普通角色不得修改对应月度编制。
- 授权角色可以解冻或调整，必须记录原因和日志。
- 招聘需求只显示冻结提示，不阻断创建或推进。

### 3.10 收入目标

- 每个叶子组织可以维护年度和月度收入目标。
- 每条目标包含金额、币种、生效信息和版本。
- 上级组织不手工录入，按下级目标自动汇总。
- 汇总结果按币种分别呈现，不进行汇率折算。
- 目标调整保留历史版本和快照。
- 后续可扩展汇率折算，但不属于第一阶段。

## 4. 快照与历史

### 4.1 快照时点

- 系统在月初和月末自动生成快照。
- 月份边界按照快照策略中配置的时区计算，不写死为服务器时区。
- 每个快照批次保存所用时区、边界时刻和规则版本。
- 管理员可以按权限手工补跑或生成修订版本。

### 4.2 快照范围

快照至少包含：

- 组织及当前层级。
- 组织与法人关系。
- 组织与成本中心关系及比例。
- 收入目标版本。
- 月度编制。
- 在职、待入职及其他人员统计。
- 员工组织、职务、法人和汇报关系。

### 4.3 快照修订

历史月份错误按以下方式修订：

1. 永久保留原始月初、月末快照。
2. 先更正源业务数据，不直接修改快照记录。
3. 授权用户生成新的快照修订版本。
4. 记录修订原因、操作者以及与原版本的关系。
5. 将修订版本重新冻结。

## 5. 数据导入与导出

### 5.1 初始化导入

- 先完成整批校验。
- 任一阻断错误存在时，整批不入库。
- 返回行号、字段、错误码和修改建议。
- 修正后重新提交。
- 导入成功后生成批次号和审计记录。

### 5.2 日常批量维护

- 允许正确行成功、错误行退回。
- 必须提供成功数、失败数和错误明细。
- 每行操作具备幂等标识，避免重复导入。

### 5.3 第一阶段重点模板

- 组织
- 法人
- 成本中心及分摊
- 职务体系
- 月度编制
- 收入目标
- 自然人和雇佣档案
- 当前人员关系

具体字段以后续生产表结构为准。

## 6. 权限与审计

### 6.1 首批用户

- 系统管理员
- SSC管理员

第一阶段不预置只读审计员，优先完成并验收系统管理员权限；SSC仍为首批业务管理角色。
权限模型仍需支持后续自定义角色和只读审计角色。

### 6.2 权限能力

架构应支持：

- 菜单和功能权限。
- 新增、查看、修改、删除、导入、导出等动作权限。
- 按组织、下级组织、法人、BP服务范围等数据范围授权。
- 字段级查看、明文查看、修改和导出权限。
- 月结解冻等高风险独立权限。

### 6.3 敏感信息

- 身份证件、银行卡、薪资等敏感字段加密存储。
- 页面默认脱敏。
- 查看明文、导出和打印必须有独立权限并写访问日志。
- 加密方式、密钥管理及字段分级在安全设计中冻结。

### 6.4 修改与更正

- SSC默认可以修改被授权的信息。
- 系统记录修改前值、修改后值、操作人、时间、来源和原因。
- 界面引导核心人事关系优先走更正事件。
- 第一阶段不强制所有修改必须走事件。

## 7. 招聘需求

第一阶段只管理招聘需求本身：

- 创建需求。
- 选择组织和职务。
- 录入需求人数、期望到岗日期和原因。
- 展示相关编制数据，但不校验或阻断。
- 跟踪需求状态。
- 关闭或取消需求。

第一阶段采用招聘需求状态机，但不创建审批实例。启用路径为：

```text
草稿 → 已通过 → 招聘中 → 已完成
草稿/已通过/招聘中 → 已取消
```

`审批中`、`已驳回`和`已撤回`作为预留状态，第二阶段接入流程引擎后启用。候选人、面试、Offer和入职衔接也属于第二阶段。

## 8. 非功能需求

### 8.1 数据

- 业务数据不得物理删除。
- 所有主数据关系必须支持生效区间。
- 同一维度的有效区间不得非法重叠。
- 数据库变更必须使用迁移工具。

### 8.2 安全

- 不允许使用默认管理员密码或固定密钥进入生产。
- 可移植研究包中的凭据不得复用。
- 所有管理端接口必须鉴权。
- 高风险操作必须记录审计。

### 8.3 可测试性

- 核心规则必须具备单元测试。
- API必须具备集成测试。
- 核心页面必须具备端到端测试。
- 导入、快照、生效日期和权限必须有异常用例。
- 第三、四阶段前增加万人在线目标的专项压测。

## 9. 第一阶段验收原则

- 不以“页面能够打开”作为完成标准。
- 每个模块必须有可重复的业务验收场景。
- 数据迁移、权限、历史、生效日期、导入和审计属于功能的一部分。
- 等待真实字段、流程图或接口资料的模块不得形成字段级最终开发任务；不受影响的基础能力可以继续拆解。
