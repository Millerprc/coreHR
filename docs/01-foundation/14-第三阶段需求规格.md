# HRIS 第三阶段需求规格

> 状态：`PARTIAL / ENTERPRISE_INPUT_PENDING`
>
> 版本：v0.1-draft
>
> 日期：2026-08-13
>
> 读者：产品决策人、业务分析、架构设计、开发与测试
>
> 注意：当前日报/月报只具备通用工程计算能力；企业规则和验收案例确认前，不得作为薪酬输入

## 1. 阶段目标

在第一阶段人员、劳动关系和组织主数据以及第二阶段请假/人事事件之上，建立可版本化、可重算、可冻结和可追溯的考勤管理能力，使系统管理员和SSC能够：

- 按时区和生效日期维护考勤规则与班次。
- 安排员工班次并接收不可变的原始打卡证据。
- 维护假期类型、请假、销假、假期余额账户和流水。
- 计算并复核员工考勤日报和月报。
- 在月结或特殊时点冻结结果，有因解冻、重算和重新冻结。
- 追溯计算使用的排班、打卡、假勤、规则版本和修订历史。

第三阶段不负责将考勤异常换算为工资扣款、加班费或薪酬结果。

## 2. 状态口径

| 状态 | 含义 |
|---|---|
| `CONFIRMED` | 用户已确认，可进入企业规则基线 |
| `IMPLEMENTED_GENERIC` | 当前系统已有通用能力，但企业口径尚未验收 |
| `PENDING_ENTERPRISE_INPUT` | 必须由企业提供制度或案例，不允许开发者猜测 |
| `DEFERRED` | 延后到其他阶段或专项任务 |

## 3. 领域边界

### 3.1 纳入范围

| 领域 | 第三阶段能力 |
|---|---|
| 规则 | 规则集、版本、生效区间、适用范围、时区和工作日历引用 |
| 班次 | 上下班、跨午夜、休息、弹性和取卡窗口 |
| 排班 | 员工日排班、换班、取消和来源 |
| 原始打卡 | 多来源接收、时区证据、幂等、补传和不可变原文 |
| 假期 | 假类、单位、余额模式、请假、销假和审批衔接 |
| 假期余额 | 年度账户、不可变流水、发放、调整、计提和结转 |
| 日报 | 计划、实到、迟到、早退、缺卡、缺勤、假勤和异常证据 |
| 月报 | 当前日报版本聚合、复核、版本和状态 |
| 冻结 | 月结冻结、特殊业务冻结、有因解冻、重算和重新冻结 |

### 3.2 不纳入范围

- 薪酬扣款、加班费、计薪天数和工资核算。
- 正式设备、企业微信或第三方打卡连接器；本阶段先定义接收契约。
- 员工移动打卡、请假自助和个人考勤查询门户。
- 位置围栏、活体识别、拍照或反作弊算法。
- 多国家完整法定假日和劳动法规本地化。
- 一万人并发目标的最终达标声明；需独立容量测试。

## 4. 数据与跨阶段关系

```text
Employment(active)
  ├─ 有效规则范围 → RuleSetVersion
  ├─ WorkDate → Schedule → Shift
  ├─ 原始Punch证据
  ├─ 已批准Leave / Cancellation
  └─ DailyResult(versioned)
            ↓
      MonthlyResult(versioned)
            ↓
        PeriodFreeze
```

- 考勤人员以有效劳动关系为基础，不另建员工主档。
- 调动、借调、离职等第二阶段事件到达生效日期后，影响后续规则适用和排班，不改写已冻结历史。
- 原始打卡是证据，不因重算、销假或解冻被修改或删除。
- 日报和月报是可重建结果，必须保存版本及所用证据引用。

## 5. 规则集、适用范围与时区

| 编号 | 状态 | 需求 |
|---|---|---|
| P3-RULE-001 | `IMPLEMENTED_GENERIC` | 规则集使用稳定代码，支持草稿、版本、发布、生效日期和IANA时区 |
| P3-RULE-002 | `CONFIRMED` | 月份和日期边界按规则配置的时区解释，不使用服务器本地时区 |
| P3-RULE-003 | `IMPLEMENTED_GENERIC` | 已发布版本不得原地修改；规则调整创建新版本 |
| P3-RULE-004 | `PENDING_ENTERPRISE_INPUT` | 规则适用范围支持国家、法人、组织、人员类型和个人例外，具体优先级待确认 |
| P3-RULE-005 | `PENDING_ENTERPRISE_INPUT` | 工作日历、法定节假日、调休和地区来源待确认 |
| P3-RULE-006 | `PENDING_ENTERPRISE_INPUT` | 迟到、早退、缺卡、缺勤、取整、封顶和补卡规则从正式矩阵加载，不长期依赖开放JSON |
| P3-RULE-007 | `CONFIRMED` | 冻结历史默认不因新规则发布而自动重算；解冻重算必须有原因和新版本 |

推荐但未确认的适用优先级为：`个人 > 组织 > 法人/国家 > 默认`。

| P3-SHIFT-002 | `PENDING_ENTERPRISE_INPUT` | 班次补充计划工时、休息段、弹性窗口、最早入卡、最晚出卡和取整规则 |
| P3-SHIFT-003 | `IMPLEMENTED_GENERIC` | 排班按劳动关系和工作日期关联一个有效班次，并记录来源和状态 |
| P3-SHIFT-004 | `PENDING_ENTERPRISE_INPUT` | 同日多班次、换班、临时取消、休息日加班和无排班打卡处理待确认 |
| P3-SHIFT-005 | `PENDING_ENTERPRISE_INPUT` | 排班批量导入、排班周期模板和覆盖冲突策略待业务样例 |

| P3-BAL-002 | `IMPLEMENTED_GENERIC` | 额度变化使用不可变流水，保存变动前后余额、类型、生效日期、来源、原因和幂等键 |
| P3-BAL-003 | `IMPLEMENTED_GENERIC` | 当前支持人工发放、调整、结转和计提；负数调整受控 |

| P3-BAL-005 | `PENDING_ENTERPRISE_INPUT` | 封顶、清零、结转上限、有效期、离职处理和跨年申请待确认 |

## 10. 日报计算

### 10.1 证据解析顺序

企业未提出替代顺序前，日报设计按以下顺序：

1. 找到目标日期有效劳动关系和规则时区。
2. 解析有效排班、班次和工作日历。
3. 归属原始打卡，不改写原证据。
4. 叠加已批准请假、销假及后续出差/外勤事件。
5. 应用迟到、早退、缺卡和缺勤规则。
6. 生成新的日报版本和证据引用。

### 10.2 需求

| 编号 | 状态 | 需求 |
|---|---|---|
| P3-DAY-001 | `IMPLEMENTED_GENERIC` | 日报按劳动关系和工作日期版本化，只有一个当前版本 |
| P3-DAY-002 | `IMPLEMENTED_GENERIC` | 保存状态、计划分钟、工作分钟、迟到分钟、早退分钟、异常码和证据 |
| P3-DAY-003 | `IMPLEMENTED_GENERIC` | 重算创建新版本，不覆盖原结果；相同输入的重复任务不产生不一致结果 |
| P3-DAY-004 | `PENDING_ENTERPRISE_INPUT` | 当前“最早入、最晚出、缺卡、无卡、请假并存”仅为通用算法，正式规则以企业案例为准 |
| P3-DAY-005 | `PENDING_ENTERPRISE_INPUT` | 半天、小时、出差、外勤、加班和精细异常码尚需领域输入 |
| P3-DAY-006 | `CONFIRMED` | 命中有效冻结范围时禁止生成新日报版本，解冻后方可重算 |

## 11. 月报与冻结

| 编号 | 状态 | 需求 |
|---|---|---|
| P3-MONTH-001 | `IMPLEMENTED_GENERIC` | 月报按劳动关系和自然月版本化，只聚合当前日报版本 |
| P3-MONTH-002 | `IMPLEMENTED_GENERIC` | 保存计划天数、出勤天数、请假天数、缺勤天数、迟到/早退分钟和状态 |
| P3-MONTH-003 | `PENDING_ENTERPRISE_INPUT` | 月报字段、日转月折算、截止时间、复核期和生成时点待确认 |
| P3-FRZ-001 | `CONFIRMED` | 同时支持月结冻结和特殊业务冻结 |
| P3-FRZ-002 | `IMPLEMENTED_GENERIC` | 月结冻结必须覆盖规则时区下完整自然月；特殊冻结可覆盖任意日期段 |
| P3-FRZ-003 | `IMPLEMENTED_GENERIC` | 冻结和解冻记录范围、类型、原因、操作者和时间；解冻不删除原冻结记录 |
| P3-FRZ-004 | `CONFIRMED` | 解冻后更正源证据、重算并重新冻结，永久保留原结果版本 |
| P3-FRZ-005 | `PENDING_ENTERPRISE_INPUT` | 月结发起人、复核人、冻结时点、特殊冻结触发和审批规则待确认 |

## 12. 权限与审计

- 首批优先支持系统管理员和SSC；员工自助本期不开放。
- 规则发布、批量排班、打卡补录、余额调整、日报重算、月报重算、冻结和解冻使用独立权限。
- 原始打卡、请假原因、位置/设备证据等按数据分级控制查看和导出。
- 当前`raw_payload`和请假原因尚未完成普通角色字段级权限与保留策略UAT；开放真实数据或非主管理员前必须先冻结字段合同。
- 高风险操作必须填写原因，并审计操作者、时间、Trace ID、对象、前后状态和证据版本。
- 普通角色的数据范围未来支持本人、组织、全部下级、法人和自定义范围；当前主管理员通配权限不代表该能力已验收。

## 13. 异常与补偿

| 场景 | 处理原则 |
|---|---|
| 规则或班次在目标日无效 | 日报失败并返回业务错误，不使用未知默认值 |
| 打卡重复/乱序 | 幂等接收并按时间证据归属，不修改原时间 |
| 余额不足 | `enforced`模式阻止批准；其他模式按规则记账 |
| 并发批准或余额调整 | 锁定账户版本，防止透支或重复入账 |
| 日报/月报计算中断 | 使用相同任务语义重试，旧当前版本在新版本成功前保持有效 |
| 冻结期出现补传打卡 | 接收原始证据，标记待处理，不改已冻结结果 |
| 历史更正 | 解冻、产生新结果版本、复核、重新冻结 |

## 14. 非功能需求

- 时间统一保存明确时区或UTC证据，禁止无时区打卡时间。
- 规则计算必须可复现：结果引用规则版本、班次、排班、打卡和假勤证据。
- 原始证据和余额流水不可物理删除。
- 接口和后台任务具备幂等、分页、Trace ID和稳定错误码。
- 计算器使用合成场景建立回归测试，制度文字之外以预期案例为验收主证据。
- 一万人同时打卡、查日报/月报是容量目标，不得在未定义流量模型和未压测时宣称通过。

## 15. 第三阶段完成定义

只有同时满足以下条件，第三阶段才能从“通用工程 MVP”升级为“企业业务验收通过”：

1. 规则适用范围、班次、取卡、异常、假期、计提/结转和月结规则完成版本化确认。
2. 正常、迟到、早退、缺卡、缺勤、跨午夜、半天/小时假、销假和冻结案例全部有预期结果。
3. 请假/销假审批图和办理权限完成UAT。
4. 原始打卡接口契约和失败补传策略确认并联调。
5. 日报/月报与人工期望样例逐字段对账。
6. 解冻、重算、版本和重新冻结链路通过。
7. 自动化测试、Docker复跑和第三阶段Review签字完成。

## 16. 企业输入顺序

第三阶段在入职等第二阶段核心流程确认后，按以下顺序补充：

1. 规则集适用范围、时区和工作日历。
2. 班次、打卡窗口和异常计算矩阵。
3. 假期类型、请假/销假和余额模式。
4. 自动计提、折算、封顶、清零和结转。
5. 日报/月报字段、月结和冻结规则。
6. 打卡来源与接口契约。
7. 一万人场景容量模型。

模板见[企业输入包07](../input-packs/07-attendance-rule-input.md)和[打卡接口输入包08](../input-packs/08-punch-interface-input.md)。

## 17. AI开发任务生成规则

- `CONFIRMED`条目可以形成企业规则任务和验收标准。
- `IMPLEMENTED_GENERIC`条目只能形成缺陷修复、确定性加固和合成数据UAT任务，不得据此宣布企业考勤口径完成。
- `PENDING_ENTERPRISE_INPUT`条目只允许生成规则模板、接口契约草案、原型和合成测试脚手架；禁止猜测迟到、早退、缺卡、假期、计提、结转或月结数值。
- 每个计算任务必须引用需求编号和至少一条输入—期望输出案例；只引用制度文字不能作为计算器完成证据。
- 收到用户确认后，先更新项目决策、本规格和对应输入包，再生成MinimaxCode任务卡。
