- D-108.6 私有核心交付形态＝**进程内私有包**（pip 私有源 wheel），**不拆独立RPC进程**；保留仅针对单一模块升级为独立RPC服务的后路。

### 8.7 审计 P0 修复批次与工程加固（2026-10-24）

| ID | 决策 | 状态 |
|---|---|---|
| D-109 | 审计 P0 缺陷按「域」分批修复，每批必须同时满足：①有独立用例覆盖缺陷本身（不是绕过）；②既有测试一条不弱化；③迁移链单链无分叉，迁移编号由主 agent 统一分配 | `CONFIRMED` |
| D-110 | 长任务一律走「任务表 + 独立 Worker 进程 + 可重试执行 + 管理查询」的通用后台任务框架，不再占用请求链路；框架先落地，**业务接入按域逐步迁移**，首批接入数据治理的导入执行 | `CONFIRMED` |

**D-109 决策项明细**：

- D-109.1 **整批语义（`initialize` / `daily`）**：导入批次新增执行模式字段。`initialize`＝初始化导入，任一阻断错误存在时**整批不入库**（执行前 409 拒绝，不产生任何写入）；`daily`＝日常批量维护，保持既有的部分成功语义（正确行入库、错误行标记）。存量批次回填为 `daily`，等价于既有行为。
- D-109.2 **生效时复校**：组织版本事件的校验从「只在排期时校验」改为「排期时校验 + 生效落库前复校」，复校内容为上级有效性、组织类型启用、环路与有效期冲突；复校不通过时事件保持 `planned`，当前版本不被改写。
- D-109.3 **编码避让**：导入路径回写编号序列（`ORG_NUMBER`），按本批次成功导入的纯数字历史编码最大值推进序列，使后续自动取号不与历史编码相撞；推进与导入同事务，并沿用同一把事务级 advisory lock。
- D-109.4 **不越权改动**：本批只做工程缺陷修复，不改业务语义取值、不自造企业输入、不动 Moka 调研数据、不代产品决策人执行账户级操作。

**D-110 决策项明细**：

- D-110.1 **任务载体**：新增通用后台任务表（`background_tasks`），承载任务类型、载荷、状态、尝试次数、退避时间、租约与结果；任务由**独立 Worker 进程**领取执行，不挂在 API 应用启动路径上。
- D-110.2 **并发与幂等**：任务领取用 PostgreSQL `FOR UPDATE SKIP LOCKED`，多 Worker 实例并行不会重复消费同一条任务；提交侧支持幂等键，重复提交返回同一任务而不新建。Worker 崩溃后由租约超时回收机制把任务放回待执行，避免永久卡死。
- D-110.3 **失败与补偿**：失败按指数退避重试，超过最大尝试次数置为失败并留下**受控错误码**（不含个人信息）；提供任务查询与手动重试入口，构成 PRD §11「人工补偿闭环」的最小可用形态。
- D-110.4 **接入节奏**：框架先落地，业务接入按域逐步迁移，首批接入数据治理的导入执行；**既有同步端点保持不变**，异步是新增路径而非替换，避免破坏既有契约与验收链路。报表与「未来生效」编排待框架跑稳后再迁移。

**D-111 决策项明细**：

- D-111.1 **依据**：D-004「第一批用户为系统管理员和 SSC」；审计 `D-考勤-待确认-决策-文档规范.md` §8（14.md:184 行，P0）判定「与 PRD 冲突」——`SSC_ADMIN` 此前只持有 `ONBOARDING_INITIATE` 与人员档案相关 6 码，**一个考勤权限都没有**，SSC 实际进不了考勤模块、也拿不到生命周期审批权限。
- D-111.2 **授予范围**：**仅**考勤域 8 个权限码（`ATTENDANCE_ADMIN` + 7 个高风险动作码）；**不新建角色**，只扩展既有 `SSC_ADMIN`；超级管理员 `*` 通配不受影响。
- D-111.2.1 **明确不授予 `LIFECYCLE_ADMIN`**：生命周期域有更窄的职责边界——SSC 只发起入职建档（`ONBOARDING_INITIATE`），发起终止等其它人事事件必须被拒（既有集成测试 `test_ssc_can_initiate_only_onboarding_and_creation_is_audited` 断言 SSC 创建 TERMINATION 返回 403）。授予域级 `LIFECYCLE_ADMIN` 会打破这条边界。若后续要放开生命周期，须**先拆出「发起某类人事事件」的细粒度权限码**，不能用域级码代替。
- D-111.3 **可收窄**：7 个高风险动作码保持独立授权。若后续要把「余额调整」「期间冻结与解冻」从 SSC 手上收回，只需再写一条迁移删除对应授权行，**不必改代码**。

### 8.8 冻结硬闸、私钥落袋与发布通道护栏（2026-10-24）

> 本节依据产品决策人 2026-10-24 的「全部按你的推荐继续来一轮，修复完这一轮我上去验证」授权，确定本轮三条决策的技术口径。本轮同时把 D-108（Open Core）的「私有实现不得随公开仓分发」从「计划」变成「可执行的门禁」。

| ID | 决策 | 状态 |
|---|---|---|
| D-113 | 考勤期间冻结是**硬闸**：冻结生效期间一律**禁止补录打卡**（409 `ATTENDANCE_PERIOD_FROZEN`），不再接受「先收下原始证据、事后重算」；业务日口径取打卡时刻在**业务时区**（`business_timezone`）下的自然日，与冻结区间的业务日历日直接可比；**幂等命中优先于冻结**（重复提交同一条打卡不是补卡，不得被拦） | `CONFIRMED` |
| D-114 | 授权签发公钥是**正式公钥**（不再是占位）：私钥离线保管、**永不进任何仓库**；公钥内置于公开仓，按 kid 支持并存轮换（新增 `k2` 与 `k1` 共存，旧 Token 过期后再摘除旧 kid）；签发工具放在**仓库外**，确保不随公开仓分发 | `CONFIRMED` |
| D-115 | 读路径索引按**实际查询条件**建，不按「哪些列看着该有索引」建：待办 `(assignee_ref, status, created_at)`、审计 `action` / `object_type`、打卡 `(employment_id, punched_at)`；**只建索引不改业务语义**，且不删既有单列索引 | `CONFIRMED` |

**D-113 决策项明细**：

- D-113.1 **为什么是硬闸**：月结冻结的语义是「这个账期已经定稿」。若冻结期间仍能补卡，定稿的账期随后又会被新的考勤事实改写，冻结就失去了意义。此前实现只拦「结果重算」、不拦「补录打卡」，等于冻结只锁了一半。
- D-113.2 **业务日口径**：打卡时刻按业务时区（`settings.business_timezone`，默认 `Asia/Shanghai`）折算成自然日，与冻结区间的 `date_from` / `date_to`（业务日历日）直接比较。**不用 UTC 日期**（会把本地 00:00–08:00 的夜班打卡算到前一天，冻结边界错位一天）；**不用班次时区**（补录打卡可能没有已发布排班可推导，业务时区是全仓唯一的业务日基准）。
- D-113.3 **幂等优先于冻结**：`(source, source_record_id)` 命中已有记录时直接返回，不做冻结校验 —— 重复提交**不产生新的考勤事实**，只是上游或设备重试。若冻结校验在前，调用方无法区分「已存在」与「被冻结」。
- D-113.4 **失败不留半写状态**：冻结校验在写库之前抛出，被拒后既没有打卡行也没有审计行。
- D-113.5 **不新增越权开关**：考勤域原本没有「带审批的强制补卡」概念，本轮**不新增**。误锁账期时的唯一途径是「解冻 → 补录 → 重算 → 再冻结」。若业务确实需要单点破例，须先另立决策再实现。
- D-113.6 **界面必须看得见**：被拒原因必须渲染在**弹窗内部**。此前面板级错误提示位于弹窗之外，而弹窗带遮罩 —— 提交被拒时用户看不到任何反馈，只会以为系统没反应。冻结拒绝按**业务规则拒绝**呈现（警示而非报错），并给出「先去解冻再补录」的下一步。

**D-114 决策项明细**：

- D-114.1 **占位公钥的历史**：此前 `BUILTIN_PUBLIC_KEYS["k1"]` 是开发期生成的占位公钥，私钥已丢弃 —— 任何 Token 都验签不过（fail-closed），系统实际以只读演示模式运行。占位公钥已替换为正式签发公钥。
- D-114.2 **轮换机制不变**：`COREHR_LICENSE_PUBLIC_KEYS` 与内置表是**合并**关系（同名 kid 以环境变量为准），因此轮换当天新增 `k2` 与 `k1` 并存，旧 Token 不会立刻失效。
- D-114.3 **签发工具的存放位置刻意在仓库外**：它读取私钥，因此不进入公开仓、不进入任何发布物；未来若建独立私有仓 `corehr-license`，再迁过去。
- D-114.4 **私钥在本机的处置**：私钥不落仓库，文件 ACL 收紧到当前用户 + SYSTEM。**它必须被转移离线保管并轮换** —— 开发机不应长期持有签发私钥（已登记进待确认清单）。

**D-115 决策项明细**：

- D-115.1 **待办索引**：`workflow_tasks (assignee_ref, status, created_at)`。前两列是待办查询的过滤条件，第三列是它的排序 —— 复合索引让「我的待办」变成一次有序索引扫描，连 ORDER BY 的排序都省了，列表与 count 两条语句共用它。
- D-115.2 **审计索引**：`audit_logs.action` 与 `audit_logs.object_type` **分开建**，不合成复合索引 —— 两者是互斥的独立过滤维度，合成会让「只按对象类型查」用不上前导列。
- D-115.3 **打卡索引**：`attendance_punches (employment_id, punched_at)`，把「某人某段时间的打卡」变成一次有序索引扫描。**既有单列索引不删**：单独按时间取数（如全量导出）用不上复合索引的前导列；重复维护成本记进待确认清单，等真实慢查询数据再决定收敛。
- D-115.4 **只建索引**：不改任何查询、不改业务语义、不动数据。索引是纯读路径优化。

**D-108 后续落地（私有实现防误发）**：

- D-108.1 `packages/`（私有实现）已加入根 `.gitignore`，**不进版本控制、不随公开仓分发**。它此前既未被跟踪也未被排除 —— 一次 `git add -A` 就会把商业实现提交进公开仓，而这类泄露在 GitHub 上**不可逆**。
- D-108.2 新增仓库守卫 `scripts/check-private-package-isolation.mjs`：三道闸（`.gitignore` 必须覆盖 `packages/` → git 已跟踪文件里不得出现私有路径 → 打包后复核发布物内容），并带**红绿自检**证明探测本身有效。该守卫已在本地做过一次真实的红→绿验证（强制把私有文件加入索引 → 守卫报红 → 撤销 → 恢复绿）。
- D-108.3 新增 CI（`.github/workflows/ci.yml`）：三道仓库卫生闸 + 后端迁移漂移检查与用例 + 前端类型、用例与构建。CI 跑在**公开仓模式**下（`packages/` 不在检出结果里），这正是对外分发时的真实形态。

### 8.9 批量考勤计算：范围语义与后台任务化（2026-10-24）

> 产品决策人 2026-10-24 反馈：「计算日报月报的选人有点傻逼了，一个一个选如果我 200 人的企业不完犊子了。我理解应该是默认全员，并且可以多选某些人。」本节把这条诉求落成技术口径。

| ID | 决策 | 状态 |
|---|---|---|
| D-116 | 批量考勤计算采用「**人员范围三态 + 后台任务执行**」：范围为**全员（默认）/ 指定人员 / 排除人员**；一次提交覆盖一整个人员范围，**不再逐人提交**；日报批量与月报批量**都走后台任务**；提交时预检账期冻结；单个人的失败不牵连其他人；长任务执行期间**必须续租** | `CONFIRMED` |

**D-116 决策项明细**：

- D-116.1 **问题定性**：原契约是「一次算一个人」——`AttendanceDailyCalculate.employment_id` 是单个 UUID，前端是**单选**下拉。200 人企业要点 200 次「计算日报」、200 次「计算月报」。这不是交互细节，是**规模不可用**。
- D-116.2 **范围三态而不是两态**：除了「全员」与「指定人员」，增加「**排除人员**」。只给两态的话，管理员要为了排除当天请假的 3 个人而取消勾选 197 个人 —— 200 人规模下这仍然不可用。三态各自语义正交，因此是三个独立取值而不是一个「勾选清单」。
- D-116.3 **全员口径与人员列表同源**：「全员」= 全部劳动关系，与「人员下拉」用**同一个查询**（`list_employment_options`），**不按在职状态过滤** —— 补算历史月份时必须算到已离职的人。口径若与列表不一致，管理员看到的和算出来的就不是一回事。
- D-116.4 **走后台任务而不是同步批处理**：月报一个人就要先补算当月缺失的日报（最多 31 次），200 人的一个月约 **6200 次单位计算**；同步请求必然超时。这与 **D-110**「长任务一律走任务表 + 独立 Worker + 可重试执行 + 管理查询」的既定口径一致，因此**日报批量与月报批量都走后台任务**，前端只有一条路径。
- D-116.5 **提交时预检账期冻结**：冻结的账期在**提交阶段**就返回 409 `ATTENDANCE_PERIOD_FROZEN`。任务失败是异步反馈，管理员要等好几秒才知道自己白提交了一次。预检用的是与执行时**完全相同**的冻结判定（同一把月度咨询锁 + 同一组过滤条件），不存在「提交放行、执行被拦」的缝隙。
- D-116.6 **单个人的失败不牵连其他人**：批量循环里每个人在**独立保存点**中计算，失败只回滚他本人，其余人的结果照常落库。失败按错误码计数（`failure_codes`），**不含个人信息**。
- D-116.7 **长任务必须续租**：后台任务的领取租约默认 60 秒，而批量计算要跑好几分钟；租约一到期，回收流程会把任务重排成 `pending`，另一个 Worker 会**重复执行**它 —— 而批量计算**不幂等**（每次执行都产生新版本）。因此处理器在执行过程中主动**续租**（默认 15 秒一次），且**租约已被别人抢走时必须让任务失败**（否则两个 Worker 同时在写同一批考勤结果）。
- D-116.8 **既有的单人端点保留**：`POST /daily-results/calculate` 与 `POST/monthly-results/calculate` 语义与契约**完全不变**（临时补算一个人仍然有用，且大量既有集成测试依赖它）。批量是**新增路径**，不是替换。
- D-116.9 **权限按计算类型区分**：日报批量要 `ATTENDANCE_DAILY_RECALC`，月报批量要 `ATTENDANCE_MONTHLY_RECALC`。因为权限随计算类型变化，端点不能用固定权限的依赖，改在函数体内按类型判定 —— 否则两种类型会被绑死在一起（要么都放行，要么都拦住）。
- D-116.10 **后台 Worker 纳入本机编排**：`deploy/compose.yaml` 增加 `worker` 服务（与 api 同镜像、独立进程），否则本机提交的任务永远不会被执行。生产上 Worker 的托管形态仍属 **A31** 未决项。

### 8.12 CI 稳定性：用例超时与 getByRole 的 jsdom 成本（2026-10-24）

> 触发事件：首次推送后 CI 第一次跑就红了 —— 失败步骤是**既有的** `LifecycleWorkspace.test.tsx`，跑满 15.3 秒超时。与本轮改动无关（同一份代码在 CI-2 是绿的），但它会让 CI 随机变红，必须修。

| ID | 决策 | 状态 |
|---|---|---|
| D-119 | 前端整页渲染级用例的看门狗统一放宽到 **45 秒**（全局 `testTimeout` + 各用例显式上限同步上调），**断言一条不动**；同时把 `LifecycleWorkspace` 用例里两处昂贵的 `getByRole` 换成「文本定位 + 断言它是 button」 | `CONFIRMED` |

**D-119 决策项明细**：

- D-119.1 **根因不是测试写得慢，是 jsdom 里 `getByRole` 极贵**：antd 6 的 CSS-in-JS 在运行时往 `<style>` 注入成千上万条规则，testing-library 的 `getByRole` 要为无障碍树逐个调 `getComputedStyle`（可见性判定），**单次查询实测 4.8~5.0 秒**；而 `getByText` 只需 **1 毫秒**。插桩实测：`LifecycleWorkspace` 用例里两次行内 `getByRole` 分别耗时 4843ms 与 4956ms，而 `render` 只用 507ms。
- D-119.2 **改法保持断言强度**：把 `within(row).getByRole("button", { name: "发起审批" })` 改成 `within(row).getByText("发起审批").closest("button")` —— 仍然断言「这一行里有一个叫『发起审批』的按钮」，只是不再让 testing-library 去算无障碍树。**该用例从 9.1 秒降到 683 毫秒（13 倍）**。
- D-119.3 **为什么没有把 202 处 `getByRole` 全改掉**：全仓有 202 处 `getByRole/findByRole/queryByRole` 分布在 30 个文件。`getByRole` 的语义价值正是「按无障碍角色与可访问名定位」——那是真实的可访问性断言。全量改写成文本查询会**削弱可访问性覆盖**，属于用「测试变绿」换「测试变弱」，不做。
- D-119.4 **因此改为系统性放宽看门狗**：`vitest.config.ts` 设全局 `testTimeout: 45_000`，并把 7 个文件里显式的 `15_000` / `20_000` 同步上调到 `45_000`。45 秒 = 本地最慢用例（9.7s）的 4 倍以上，足够覆盖 CI runner 约 1.7 倍的减速；真挂死的用例仍然会失败，只是晚一点。
- D-119.5 **遗留**：本次只把最慢的那一条用例做了 D-119.2 的优化。其余用例里仍有 `getByRole`，因此**单测文件耗时普遍在 1~10 秒**（例如 `AttendanceWorkspace` 9.7s、`ReportPanel` 6.8s、`ReportingWorkspace` 5.9s）。这些不是失败风险（看门狗已放宽），但**测试套件整体偏慢**（本机全量约 2.5 分钟），属于待优化项，不在本轮范围。

### 8.13 后台任务的事务边界、并发重试与幂等标识（2026-10-25）

> 触发事件：外部审计在本轮新增的后台任务 / 异步导入 / 考勤冻结代码上提出 3 个问题。
> 审计本身声明是**静态结论、未做运行时复现**；本轮逐条在真实 PostgreSQL 上复现、修复并补了回归测试。

| ID | 决策 | 状态 |
|---|---|---|
| D-121 | 后台任务框架的**事务边界**改为「**每条任务一个独立事务**」；人工重试改**原子条件更新**；重复提交标识必须指向**同一次提交**，否则返回 409 冲突 | `CONFIRMED` |

**D-121 决策项明细**：

- D-121.1 **问题一（整批共用一次提交）是真的，且有三个后果**：原实现一批任务共用一次 `commit()`。① 领取状态（`pending → running`）在整批跑完前不提交，页面看到的还是「等待中」；② 批次中途崩溃会**回滚整批** —— 前面已经算完的考勤结果连同任务状态一起消失；③ 尝试次数与领取状态在同一个事务里，崩溃时一起回滚 —— 反复崩溃的任务永远攒不够次数，「最多重试 N 次」形同虚设。
- D-121.2 **修法是拆成三段各自提交**：**领取**单独提交（状态与尝试次数立刻可见、立刻落库）→ **执行**每条任务独占一个事务并对任务行加 `FOR UPDATE` → **落结果**在同一个执行事务里提交，失败只回滚这一条。执行期间的行锁保证别的 Worker 既回收不了这条任务、也不会重复执行它。
- D-121.3 **连带修掉审计没抓到的第四个问题**：批量领取时，后面任务的租约在**轮到它之前**就可能过期（领取时统一起算，60 秒租约遇上一条要跑几分钟的任务必然过期），回收流程会把它们放回队列导致**另一个 Worker 重复执行**。改成「一次领一条、立刻执行」后，租约总是执行前才起算。这条比审计列的三条更危险 —— 批量考勤计算每次执行都产生新版本，重复执行等于重复写结果与重复审计。
- D-121.4 **崩溃循环必须收敛**：领取时只取 `attempts < max_attempts` 的任务；回收时若尝试次数已用尽，**直接置为失败**（错误码 `retry_exhausted`）而不是放回队列。进程崩溃走不到 `fail()`，这一条是「最多重试 N 次」真正生效的地方。
- D-121.5 **租约与执行者校验**：`complete()` / `fail()` 新增可选 `expected_owner`；租约已被别人抢走就**不写这条任务**（抛 `TaskLeaseLostError`），由 Worker 回滚并放弃。领取者与写结果者必须是同一个。
- D-121.6 **问题二（并发重试）是真的**：原实现「先读状态、再改成等待中」，两个并发重试会同时读到 `failed`；其中一个可能在任务**已经被 Worker 执行完之后**仍把它改回 `pending`，造成重复计算与多出一版结果。改为一条带状态条件的 `UPDATE ... WHERE status = 'failed' RETURNING ...` 让数据库做判定，**只有一个请求能改成功**，另一个拿到 409 `BACKGROUND_TASK_NOT_RETRYABLE`。
- D-121.7 **问题三（幂等标识跨批次）是真的**：原实现只要标识相同就返回旧任务。批次 B 复用批次 A 的标识时，接口返回 202「已受理」，但 **B 根本没进队列** —— 调用方以为提交成功，实际什么都没发生。改为校验 `task_type` + `batch_id` + `actor_id`，不匹配时返回 409 `BACKGROUND_TASK_IDEMPOTENCY_CONFLICT`；同一层的防线也下沉到 `TaskQueue.enqueue`（新增 `idempotency_scope` 参数）。
- D-121.8 **幂等比对只比身份字段**：`trace_id` 与 `reason` 每次请求都可能不同，**不参与比对**；否则正常重试会被误判成冲突。
- D-121.9 **红→绿验证**：新增 9 条回归测试（`apps/api/tests/integration/test_background_task_concurrency.py`），在**旧代码**上 8 条变红，且每条红的原因都精确对应审计列出的一个后果（`assert 'pending' == 'running'`、`assert 'pending' == 'succeeded'`、`assert 0 == 1`、`DID NOT RAISE ApiError` 等）；恢复修复后全绿。这批测试刻意用**真实连接**而不是共享会话 —— 共享会话的写入没有真正提交，别的连接看不见，「领取状态是否立即可见」「尝试次数是否被回滚」这类断言就测不出来。
- D-121.10 **一处语义变更（有意为之）**：租约被抢走时，任务**不再由迟到的 Worker 置为失败**，而是交给当前持有者（或回收流程）处理。理由是迟到 Worker 改写别人正在跑的任务本身就是错的；「不双写」这个 D-116 的核心诉求通过行锁 + `expected_owner` 校验达成。
- D-121.11 **顺带修掉的一个隐患**：Worker 领取后**在提交之后**才读 `rows[0].id`，一旦会话是默认的 `expire_on_commit=True`，ORM 属性会过期，访问它就变成异步上下文里的非法懒加载（`MissingGreenlet`）。现在 id 在提交前取出，不依赖 `expire_on_commit` 配置。
