# coreHR 代码结构与编码规范

> 状态：`ACTIVE`  
> 版本：v0.5
> 首次日期：2026-07-31
> 最近更新：2026-08-19
> 适用范围：第零阶段及后续所有代码、测试、迁移和脚本  
> 目标读者：Codex、代码复审者及后续经明确授权的开发者

## 1. 规范定位

本文件约束代码如何组织和实现，不补充业务规则，也不改变任务卡的文件所有权。产品和模块边界以[coreHR产品总体PRD](./16-coreHR产品总体PRD.md)为准。

规则分为两级：

- `MUST`：强制规则。违反即不能验收，除非通过ADR记录例外。
- `PREFER`：默认偏好。有更简单或更可靠的方案时可以调整，但必须在交付回执中说明。

发生冲突时，按以下顺序处理：

1. 用户最新明确确认。
2. 产品总体PRD中的产品级边界。
3. `CONFIRMED`项目决策。
4. 已批准的模块功能需求、当前原子任务及其验收标准。
5. Accepted ADR。
6. 本规范。

发现冲突时停止实现并记录，不由开发者自行选择更方便的一项。

## 2. 总体原则

### 2.1 强制原则

- `MUST`保持模块化单体，不提前拆微服务。
- `MUST`按业务能力组织模块，不按“所有Controller、所有Service、所有Model”组织整个项目。
- `MUST`让业务规则停留在领域层或应用层，路由、React页面和SQLAlchemy模型不得成为规则中心。
- `MUST`通过模块公开的应用服务协作，不跨模块直接写表。
- `MUST`使用明确类型、稳定错误码、结构化日志和确定性测试。
- `MUST`保护真实人员数据、凭据、Token、证件号、银行信息和薪酬信息，不得写入代码、测试、日志或提交记录。
- `MUST`只实现当前任务需要的能力，不为多租户、微服务、移动端、MCP或流程引擎提前建抽象框架。

### 2.2 默认偏好

- `PREFER`可读性高于技巧性。
- `PREFER`组合而非继承。
- `PREFER`不可变数据和显式返回值。
- `PREFER`先写最小可验证实现，出现第二个真实用例后再抽公共能力。
- `PREFER`短函数和提前返回，避免深层嵌套。
- `PREFER`在现有模块内增加一个清晰文件，而不是新建含义模糊的公共目录。

## 4. 后端结构

### 4.1 推荐目录

```text
apps/api/
├─ src/hris/
│  ├─ main.py
│  ├─ api/
│  │  └─ v1/
│  │     └─ router.py
│  ├─ core/
│  │  ├─ config.py               # 配置读取
│  │  ├─ errors.py               # 公共错误模型和异常映射
│  │  ├─ logging.py              # 结构化日志
│  │  └─ security.py             # 身份安全公共能力
│  ├─ shared/
│  │  ├─ db/                     # Session、基类和迁移公共能力
│  │  └─ kernel/                 # 极少量稳定的跨模块契约
│  └─ modules/
│     └─ <module_name>/
│        ├─ api.py               # HTTP适配层
│        ├─ schemas.py           # 请求与响应模型
│        ├─ service.py           # 用例编排和事务边界
│        ├─ domain.py            # 实体、值对象和业务不变量
│        ├─ repository.py        # 仓储接口
│        └─ models.py            # SQLAlchemy持久化模型
├─ tests/
│  ├─ unit/
│  ├─ integration/
│  └─ contract/
├─ alembic/
└─ pyproject.toml
```

小模块从上述单文件结构开始。只有单文件职责明显过多时，才把对应文件拆成同名目录，例如将`service.py`拆为`application/commands.py`和`application/queries.py`。

### 4.2 依赖方向

```text
HTTP路由
   ↓
应用服务
   ↓
领域规则 ← 仓储接口
              ↑
       SQLAlchemy仓储实现
```

- `api.py`可以依赖`schemas.py`和`service.py`。
- `service.py`可以依赖领域对象和仓储接口。
- `domain.py`不得依赖FastAPI、SQLAlchemy、Redis或HTTP。
- `models.py`不得承载业务流程和权限判断。
- 仓储负责数据访问，不负责提交事务；事务由应用服务或Unit of Work控制。
- 模块A不得导入模块B的SQLAlchemy模型或仓储实现，只能调用B公开的应用服务或稳定契约。

### 4.2.1 产品模块依赖

目标依赖方向：

```text
Workforce Core                            → Platform Kernel
Workflow                                  → Platform Kernel
Recruitment / Contract / Attendance       → Platform Kernel + Workforce Core
Payroll                                   → Platform Kernel + Workforce Core + Attendance
ESS                                       → Platform Kernel + Workforce Core + 已启用套件
Integration                               → Platform Kernel + 目标套件公开合同
Recruitment / Contract / Attendance / Payroll ──可选→ Workflow
```

- Platform Kernel不得导入任何HR业务套件实现。
- Workforce Core不得依赖Recruitment、Attendance、Payroll等可选套件。
- 跨模块写入只能调用数据所有者的公开命令接口；跨模块读取使用公开查询接口、只读投影或批准的稳定合同。
- P0完成后，每个模块必须通过`ModuleManifest`声明模块ID、版本、依赖、路由、迁移和前端入口。
- P0完成前不得新增跨模块直接模型引用；必要的新协作先定义最小公开合同。
- 以上是代码依赖规则，不表示需要立即拆成独立进程或动态插件。

### 4.3 路由规则

路由只负责：

1. 接收并校验HTTP输入。
2. 获取当前用户和请求上下文。
3. 调用一个明确的应用用例。
4. 映射HTTP状态和响应模型。

路由不得：

- 直接执行SQL。
- 拼装跨表业务结果。
- 编写有效期、权限、状态转换或编号生成规则。
- 捕获异常后返回永远成功的`200`。

示例：

```python
@router.post(
    "/dictionary-items",
    response_model=DictionaryItemResponse,
    status_code=status.HTTP_201_CREATED,
)
def create_dictionary_item(
    payload: CreateDictionaryItemRequest,
    service: DictionaryItemService = Depends(get_dictionary_item_service),
) -> DictionaryItemResponse:
    item = service.create(
        CreateDictionaryItemCommand(
            dictionary_code=payload.dictionary_code,
            item_code=payload.item_code,
            display_name=payload.display_name,
        )
    )
    return DictionaryItemResponse.model_validate(item)
```

### 4.4 应用服务规则

- 一个公开方法表达一个用例，例如`create_item`、`disable_account`、`assign_role`。
- 写操作必须有明确事务边界；失败时不得留下部分结果。
- 幂等请求必须使用业务幂等键或请求幂等键，不依赖“先查再写”的竞态实现。
- 权限在服务端校验；前端隐藏按钮不能代替权限。
- 应用服务返回领域对象或明确的读取模型，不返回FastAPI `Response`。

示例：

```python
@dataclass(frozen=True)
class CreateDictionaryItemCommand:
    dictionary_code: str
    item_code: str
    display_name: str


class DictionaryItemService:
    def __init__(
        self,
        repository: DictionaryItemRepository,
        unit_of_work: UnitOfWork,
    ) -> None:
        self._repository = repository
        self._unit_of_work = unit_of_work

    def create(self, command: CreateDictionaryItemCommand) -> DictionaryItem:
        if self._repository.exists(command.dictionary_code, command.item_code):
            raise ConflictError(code="DICTIONARY_ITEM_CODE_EXISTS")

        item = DictionaryItem.create(
            dictionary_code=command.dictionary_code,
            item_code=command.item_code,
            display_name=command.display_name,
        )
        self._repository.add(item)
        self._unit_of_work.commit()
        return item
```

### 4.5 数据和类型

- 所有公开函数、方法和类属性必须有类型标注。
- `Any`只允许出现在无法控制的第三方边界，并必须尽快转换为明确类型。
- 金额使用`Decimal`，不得使用浮点数。
- 时间点使用带时区的`datetime`并以UTC入库。
- 业务日期使用`date`，不得为方便统一转换成UTC时间点。
- 稳定代码与显示名称分离，代码不得因中文名称调整而改变。
- Pydantic请求/响应模型、领域对象和SQLAlchemy模型分离，不直接把ORM对象作为公共API契约。
- 数据库约束负责最后一道完整性保护，应用层错误负责给用户可理解的反馈。

### 4.6 数据库与迁移

- 所有结构变更必须通过Alembic迁移，不允许应用启动时自动建表或改表。
- 每个迁移只服务于一个可解释变更，并包含约束、索引和数据兼容性说明。
- 表、列、索引、约束统一使用`snake_case`。
- 外键、唯一约束和防重逻辑必须在数据库层有相应保护。
- 不使用无界级联删除；历史、审计、快照和已生效业务数据不得被级联物理删除。
- 生产数据变更必须可重试；破坏性迁移必须单独审批并提供备份或恢复方案。
- 查询只选择需要的列，列表接口避免N+1，分页必须有稳定排序。

### 4.7 错误与日志

公共错误响应遵循：

```json
{
  "code": "DICTIONARY_ITEM_CODE_EXISTS",
  "message": "字典项代码已存在",
  "details": [],
  "trace_id": "01J..."
}
```

- 错误码使用大写`SNAKE_CASE`且发布后保持稳定。
- 预期业务错误映射为明确的4xx状态；未知异常统一映射为500。
- 不吞异常，不使用空`except`，不把失败静默降级为成功。
- 日志使用结构化字段，至少可关联`trace_id`、用户、动作和业务对象。
- 日志不得记录密码、Token、完整证件号、银行账户、薪酬明细或请求体中的敏感字段。

## 5. 前端结构

### 5.1 推荐目录

```text
apps/web/src/
├─ app/
│  ├─ providers/                 # Router、Query、主题等根Provider
│  ├─ router/                    # 路由声明和守卫
│  └─ layouts/                   # 管理端整体布局
├─ pages/                        # 路由页面，只做页面编排
├─ features/
│  └─ <feature-name>/
│     ├─ api/                    # 本功能API调用
│     ├─ components/             # 功能组件
│     ├─ hooks/                  # 功能Hook
│     ├─ model/                  # 类型、转换和局部状态
│     └─ tests/
├─ shared/
│  ├─ api/                       # HTTP客户端、生成契约和公共拦截
│  ├─ components/                # 真正跨功能复用的组件
│  ├─ hooks/
│  ├─ lib/
│  ├─ styles/
│  └─ types/
└─ main.tsx
```

依赖方向：

```text
app → pages → features → shared
```

- `shared`不得依赖`features`或`pages`。
- 功能之间不得直接读取对方内部状态；通过公开组件、Hook或API契约协作。
- 页面负责组合，不直接实现复杂表单、请求状态或业务转换。
- 不建立全局`components`垃圾场；组件应优先放在所属`feature`。

### 5.2 React与TypeScript

- 组件、Props、Hook返回值和API数据必须有明确类型。
- 禁止使用`any`规避类型检查；禁止无理由使用非空断言`!`。
- Props保持只读，数组和对象状态不得原地修改。
- 基于旧状态更新时使用函数式更新。
- `useEffect`只用于与外部系统同步，不用于派生普通展示数据。
- 服务端数据由统一数据请求层管理，不重复复制到全局状态。
- 仅在有真实渲染成本时使用`memo`、`useMemo`和`useCallback`，不得机械包裹所有组件。
- 大表格需要服务端分页；达到实际性能阈值后再引入虚拟滚动。

示例：

```tsx
interface DictionaryItemStatusProps {
  readonly enabled: boolean
}

export function DictionaryItemStatus({
  enabled,
}: DictionaryItemStatusProps): React.JSX.Element {
  return (
    <Tag color={enabled ? "success" : "default"}>
      {enabled ? "启用" : "停用"}
    </Tag>
  )
}
```

状态更新：

```tsx
setSelectedCodes((currentCodes) => [...currentCodes, newCode])
```

禁止：

```tsx
selectedCodes.push(newCode)
setSelectedCodes(selectedCodes)
```

### 5.3 API访问

- 所有请求经统一HTTP客户端发送，页面和展示组件不得直接散落`fetch`调用。
- `/api/v1`契约生成机制启用后，API类型优先由OpenAPI生成，不手写重复接口类型。
- 401、403、409、422和500必须有统一处理策略，同时允许功能层展示具体业务错误。
- 请求必须支持取消或忽略过期结果，避免快速切换条件时旧响应覆盖新状态。
- 不在浏览器日志、错误提示或本地持久化中保存敏感明文。

示例：

```ts
export async function getDictionaryItems(
  dictionaryCode: string,
  signal?: AbortSignal,
): Promise<DictionaryItem[]> {
  return apiClient.get<DictionaryItem[]>(
    `/api/v1/dictionaries/${dictionaryCode}/items`,
    { signal },
  )
}
```

### 5.4 Ant Design使用偏好

- 设计决策以Ant Design官方当前稳定文档为准；编码API必须兼容`apps/web/package.json`锁定的版本。依赖升级必须单独立项，并通过类型检查、生产构建、组件测试和关键E2E旅程后才能合入。
- 优先使用Ant Design原生组件和Token，不复制一套相同基础组件。
- 只有需要统一权限、审计、脱敏或交互行为时，才封装业务组件。
- 颜色、间距、圆角和字体从主题Token获取，不在页面散落魔法数。
- 表单字段标签、帮助、校验反馈和必填状态必须清晰。
- 表格必须处理加载、空数据、错误、分页和无权限状态。
- 高风险操作必须二次确认，并明确说明对象和影响。
- 不只用颜色表达状态；键盘操作、焦点、语义标签和对比度应满足可访问性要求。

### 5.5 页面载体与导航

- 列表、组织树、仪表盘和工作台是宿主页；宿主页不得因打开新增、编辑、详情、流程或子任务而在当前标签页被替换。
- `Modal`用于简短确认、单一决策或轻量表单；`Drawer`用于需要保留宿主页上下文的预览和中等复杂编辑。二者统一称为“弹窗类容器”。
- 多分区详情、长表单、页内标签、历史/审计对比、多步骤流程、打印导出或需要同时参照宿主页的任务，使用具有稳定路由的新浏览器标签页。
- 禁止多层嵌套Modal/Drawer。需要第二层复杂交互时，改用新浏览器标签页；简单确认框不计为第二层业务容器。
- 新标签页必须由用户操作直接触发，使用稳定、可刷新、可分享的受控路由；调用`window.open`时使用`noopener,noreferrer`，不得依赖`window.opener`传递敏感数据或唯一状态。
- 弹窗打开后焦点进入容器，关闭后回到触发元素；提交中禁止重复操作。关闭含未保存修改的容器或标签页前必须提示。
- Modal/Drawer内的表单必须明确关闭后的状态策略。需要每次重置时，使用当前锁定版本支持的销毁/重置能力，并为表单编写“关闭后重新打开”的组件测试。
- 每个页面实现必须引用功能需求中批准的`MODAL`、`DRAWER`或`NEW_TAB`载体，不得在编码阶段自行改变。
- 每个新增或变更的前端页面必须引用功能需求中状态为`PROTOTYPE_APPROVED`的Pencil文件、画板ID和版本；没有已批准原型不得开始页面编码。
- 实现必须与已批准原型的信息层级、主要操作和交互载体一致。代码阶段发现原型需要变化时，先更新需求与原型版本，再修改实现和对应需求追踪注释。

完整选择矩阵和验收项见[Ant Design页面与交互载体规范](../design/antd-page-interaction-standard.md)。

## 6. 命名与格式

### 6.1 Python

| 对象 | 规则 | 示例 |
|---|---|---|
| 文件、函数、变量 | `snake_case` | `dictionary_item.py` |
| 类、异常 | `PascalCase` | `DictionaryItemService` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_IMPORT_ROWS` |
| 私有成员 | 单下划线前缀 | `_repository` |

### 6.2 TypeScript

| 对象 | 规则 | 示例 |
|---|---|---|
| React组件 | `PascalCase.tsx` | `DictionaryItemTable.tsx` |
| Hook | `useXxx.ts` | `useDictionaryItems.ts` |
| 普通文件、函数、变量 | `camelCase` | `formatBusinessDate.ts` |
| 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_PAGE_SIZE` |
| 功能目录 | `kebab-case` | `dictionary-management/` |

补充规则：

- 布尔值使用`is`、`has`、`can`或`should`前缀。
- 函数使用动词开头，例如`createItem`、`calculateHeadcount`、`isPeriodOverlapping`。
- 禁止`data1`、`temp`、`obj`、`info`、`handleData`等无法表达领域含义的名字。
- 缩写只有在项目内含义唯一时使用；同一概念不得同时出现`employee`、`emp`、`staff`三种命名。
- 格式由工具统一执行，不在代码审查中争论个人空格偏好。

## 7. 注释与文档

- 注释解释“为什么”和业务约束，不逐行复述代码。
- 已失效的注释和注释掉的旧代码必须删除，历史由Git保存。
- 公共API、复杂有效期算法、并发控制和安全边界需要简短说明。
- `TODO`必须包含任务编号或明确条件，禁止无归属永久TODO。
- 新增环境变量必须同步`.env.example`和README，示例值不得是有效凭据。
- 影响架构、依赖、数据兼容性或安全边界的决定必须新增或修订ADR。

### 7.1 需求追踪注释

新需求或已批准需求变更导致生产代码、数据库迁移、运行配置或接口合同发生变化时，必须在实际规则落点附近增加或更新需求追踪注释。

统一格式：

```text
Requirement: <功能/规则/决策ID> — <为什么需要这段实现，以及本次改变了什么业务语义>
```

示例：

```python
# Requirement: WFC-ORG-F001-BR003 / D-009 — 同一有效期间只允许一个直接上级。
parent_id = validate_single_parent(command.parent_id)
```

```typescript
// Requirement: ATT-PUNCH-F002-PERM001 — 补卡入口只对具备补卡权限的角色展示。
const canSubmitCorrection = permissions.includes('ATTENDANCE_PUNCH_CORRECT')
```

强制规则：

- 每个因需求新增或变更而修改的生产代码文件，至少在承载该需求的规则分支、公开接口、迁移、约束或配置处有一条追踪注释。
- 注释必须引用稳定功能、业务规则、权限、异常或项目决策ID；只有任务ID而没有需求ID不合格。
- 同一需求在一个文件内集中实现时写在最接近规则入口的位置，不要求逐行重复。
- 数据库迁移在迁移模块说明或对应DDL附近记录；生成代码不得手改，应在生成源、适配层或调用入口记录。
- 需求语义再次变化时同步更新注释；规则被移除时删除或改为指向替代需求，禁止保留失效说明。
- 纯重命名、格式化、依赖锁定和不改变行为的机械重构不伪造需求注释，但交付回执必须说明其不承载需求变化。
- 注释不能替代功能文档、自动化测试、迁移说明、ADR或交付回执。

## 8. 测试规范

### 8.1 测试层级

| 层级 | 主要验证 | 外部依赖 |
|---|---|---|
| 单元测试 | 领域规则、计算、状态转换、纯组件 | 不访问网络和真实数据库 |
| 集成测试 | SQLAlchemy仓储、事务、Redis、API路由 | 使用隔离PostgreSQL/Redis |
| 契约测试 | OpenAPI、错误结构、前后端生成客户端 | 使用固定契约 |
| 端到端测试 | 管理员关键旅程 | 使用专用测试数据 |

### 8.2 强制规则

- 新增规则必须有正常、边界和失败用例。
- 修复缺陷必须先增加能复现缺陷的回归测试。
- 测试使用合成数据，不复制真实人员资料。
- 测试不得依赖执行顺序、当前日期、外部互联网或固定`sleep`。
- 时间、随机数、流水号和当前用户通过可替换依赖控制。
- 每个测试只验证一个清晰行为，名称描述条件和期望结果。
- 数据库测试必须隔离并清理，不得共享开发库状态。
- 禁止为了通过检查而删除断言、跳过测试或降低质量门槛。

示例：

```python
def test_create_item_rejects_duplicate_code() -> None:
    # Arrange
    repository = InMemoryDictionaryItemRepository(
        existing_codes={("employee_type", "FORMAL")}
    )
    service = DictionaryItemService(repository, FakeUnitOfWork())

    # Act / Assert
    with pytest.raises(ConflictError) as error:
        service.create(
            CreateDictionaryItemCommand(
                dictionary_code="employee_type",
                item_code="FORMAL",
                display_name="正式员工",
            )
        )

    assert error.value.code == "DICTIONARY_ITEM_CODE_EXISTS"
```

## 10. Git与任务边界

- 一个原子任务使用一个独立分支和一个可独立审查的变更集。
- 默认分支受保护；复审通过前不得把`Proposed`结果当作已验收基线。
- 提交使用Conventional Commits，例如：

```text
feat(auth): add local account lockout
fix(audit): preserve actor id on failed operation
test(dictionary): cover duplicate item code
docs(adr): record dependency lock strategy
```

- 不修改任务所有权之外的文件；确需修改时先说明原因和影响。
- 不混入无关重构、格式化或依赖升级。
- 不重写他人提交历史，不覆盖用户未提交改动。
- 生成代码必须与生成源和生成命令同时提交，禁止手工修改生成文件。

## 11. Codex原子任务要求

每张任务卡必须至少包含：

```text
任务编号：
目标：
输入文档：
允许修改文件：
禁止修改文件：
实现规则：
验收用例：
执行命令：
交付证据：
已知限制：
```

每个任务默认只交付一个可描述的能力，例如：

- 一个数据库迁移及对应模型。
- 一个应用用例及其API。
- 一个页面或一个独立交互组件。
- 一组围绕同一规则的测试。

Codex及后续开发执行者不得：

- 根据“常见HR系统做法”补字段、枚举、状态或审批。
- 为了复用而提前建立通用规则引擎。
- 在路由、页面或迁移中藏入未记录的业务默认值。
- 用模拟成功、空实现、吞异常或跳过测试满足验收。
- 先合并到`main`再请求复审。

## 12. 代码审查清单

每次交付至少检查：

- [ ] 变更只覆盖任务范围。
- [ ] 目录和依赖方向符合本规范。
- [ ] 业务规则不在路由、页面或ORM模型中散落。
- [ ] 输入、返回值和错误均有明确类型与稳定契约。
- [ ] 写操作有事务、并发、防重和权限考虑。
- [ ] 没有跨模块写表、N+1或无界查询。
- [ ] 没有敏感信息进入日志、错误、测试或仓库。
- [ ] 正常、边界、失败和权限用例已覆盖。
- [ ] 格式、静态检查、类型检查、测试、构建和迁移检查全部通过。
- [ ] README、`.env.example`、OpenAPI、ADR和交付回执按影响同步。
- [ ] 需求驱动的代码变化已在实际规则落点添加或更新需求追踪注释，并引用稳定需求/决策ID。
- [ ] 复跑命令可在干净环境执行并正确清理。

不满足任一强制项时，交付状态保持`Proposed`，不得标记完成。
