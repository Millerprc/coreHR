# HRIS 第二阶段需求规格

> 状态：`PARTIAL / ENTERPRISE_INPUT_PENDING`
>
> 版本：v0.1-draft
>
> 日期：2026-08-13
>
> 读者：产品决策人、业务分析、架构设计、开发与测试
>
> 注意：通用工程能力已经实现；未确认的企业流程不得被本文件或当前代码推定为正式规则

## 1. 阶段目标

在第一阶段组织、职务、人员、劳动/协议关系和招聘需求主数据之上，建立可配置、可追溯的人员生命周期能力，使系统管理员和SSC能够：

- 管理候选人、应聘、Offer确认和转待入职记录。
- 配置并发布人事流程，处理会签、或签和条件分支。
- 通过人事事件执行入职、转正、调动、兼岗、借调、离职、撤回和更正。
- 按场景选择直接生效、审批生效和未来生效。
- 对已生效业务执行受控回退，不覆盖原历史。
- 管理劳动合同和其他协议的建档、变更、续签、解除、取消与到期提醒。
- 保留流程实例、审批任务、业务结果、同步记录和审计之间的完整链路。

第二阶段的目标不是建设任意脚本或通用低代码平台，而是为HR领域提供受控流程和事件执行能力。

## 2. 状态口径

| 状态 | 含义 |
|---|---|
| `CONFIRMED` | 用户已确认，可作为企业规则基线 |
| `IMPLEMENTED_GENERIC` | 当前系统已有通用实现，但仍需企业输入才能验收为正式流程 |
| `PENDING_ENTERPRISE_INPUT` | 必须由企业提供，不允许开发者猜测 |
| `DEFERRED` | 已明确不属于第二阶段 |

## 3. 领域边界

### 3.1 纳入范围

| 领域 | 第二阶段能力 |
|---|---|
| 流程定义 | 定义、版本、节点、连线、条件、发布和停用 |
| 流程运行 | 实例、审批任务、会签/或签、选路、通过、驳回和审计 |
| 应聘管理 | 候选人、应聘、阶段、Offer信息和录用转换 |
| 人事事件 | 入职、转正、调动、兼岗、借调、结束任职、离职、撤回和更正 |
| 生效机制 | 直接、审批、今天、未来日期、失败重试和幂等 |
| 回退 | 补偿事件、历史版本恢复或组合策略；直接或审批生效 |
| 合同/协议 | 建档、版本、变更、续签、解除、取消、到期和提醒 |
| 流程数据 | 业务对象、实例、任务、事件、审计和下游同步链路 |

### 3.2 不纳入范围

- 招聘门户、外部候选人自助和面试官移动端。
- 员工自助发起、查看或修改人事流程。
- 薪酬、社保、个税和费用计算。
- 电子签章平台、附件对象存储和病毒扫描的最终实现。
- 企业微信、自建OA及其他下游连接器的正式接入。
- 任意脚本节点、SQL条件或无代码表单引擎。
- 多租户、完整多语言和多数据库兼容。

## 4. 跨阶段依赖

第二阶段必须复用第一阶段事实，不得复制人员或组织主数据：

```text
招聘需求 → 候选人 → 应聘 → Offer确认
                           ↓
Person → Employment(pending_start) → 主任职
                           ↓
                    ONBOARDING事件
                           ↓
                  Employment(active)
```

- 组织、职务、法人和Person以第一阶段稳定ID为准。
- Offer确认不是入职生效；它只创建或复用待入职档案。
- 人事流程改变第一阶段当前结果时，必须通过领域事件服务写入，不得由流程引擎直接更新任意表。
- 第三阶段考勤只读取已生效的劳动关系、任职和人事事件结果。

## 5. 流程定义与运行

| 编号 | 状态 | 需求 |
|---|---|---|
| P2-FLOW-001 | `IMPLEMENTED_GENERIC` | 流程定义使用稳定代码，包含名称、业务类别、状态和当前发布版本 |
| P2-FLOW-002 | `IMPLEMENTED_GENERIC` | 修改已发布流程时创建新版本，不原地覆盖运行中实例引用的版本 |
| P2-FLOW-003 | `IMPLEMENTED_GENERIC` | 节点类型限制为开始、审批、受控动作和结束；当前一个版本恰有一个开始节点和一个结束节点 |
| P2-FLOW-004 | `IMPLEMENTED_GENERIC` | 发布前校验缺失节点、断线、歧义条件、无默认线及其他无效图结构 |
| P2-FLOW-005 | `CONFIRMED` | 审批节点同时支持会签`all`和或签`any` |
| P2-FLOW-006 | `IMPLEMENTED_GENERIC` | 条件使用结构化字段路径、运算符和值，不执行SQL、脚本或函数 |
| P2-FLOW-007 | `IMPLEMENTED_GENERIC` | 条件分支最多命中一条；无命中时走唯一默认线；多条命中时失败关闭 |
| P2-FLOW-008 | `IMPLEMENTED_GENERIC` | 流程实例固定引用启动时的发布版本，并保留选路历史 |
| P2-FLOW-009 | `IMPLEMENTED_GENERIC` | 审批任务记录节点、办理人引用、决定、意见、实际办理人和时间 |
| P2-FLOW-010 | `PENDING_ENTERPRISE_INPUT` | 动态办理人必须从已确认的组织、负责人、BP或角色关系解析，并定义缺失时的兜底角色 |
| P2-FLOW-011 | `PENDING_ENTERPRISE_INPUT` | 任务只能由实际办理人、有效代理人或授权管理员处理；当前主管理员通用操作不代表最终权限模型 |
| P2-FLOW-012 | `PENDING_ENTERPRISE_INPUT` | 撤回、重新提交、转办、加签、减签、超时、催办和升级按流程逐项确认 |

当前流程不支持两条独立业务支线并行后汇合。节点内多人会签不等于并行流程。

## 6. 候选人、应聘与录用

| 编号 | 状态 | 需求 |
|---|---|---|
| P2-REC-001 | `IMPLEMENTED_GENERIC` | 候选人具有独立编号、展示名称、通用联系方式载荷、状态和可选Person关联；当前载荷未形成企业敏感字段合同 |
| P2-REC-002 | `IMPLEMENTED_GENERIC` | 一个候选人可以对不同招聘需求产生应聘记录；同一候选人和同一需求不得重复建档 |
| P2-REC-003 | `IMPLEMENTED_GENERIC` | 应聘记录保存当前阶段、状态和Offer结构化信息；企业阶段名称和字段待确认 |
| P2-REC-004 | `CONFIRMED` | 招聘需求与编制保持弱关联，录用转换不因无空编被阻断 |
| P2-REC-005 | `IMPLEMENTED_GENERIC` | 普通状态修改不得直接把应聘标记为已录用；必须执行显式Offer确认/录用转换命令 |
| P2-REC-006 | `IMPLEMENTED_GENERIC` | 录用转换在同一事务中创建或复用Person、六位工号、待入职Employment和目标组织/职务主任职 |
| P2-REC-007 | `CONFIRMED` | 二次入职复用原Person和原工号 |
| P2-REC-008 | `IMPLEMENTED_GENERIC` | 新人录用必须提供计划入职日有效的已核验主要证件；复聘可以复用有效证件 |
| P2-REC-009 | `IMPLEMENTED_GENERIC` | 录用转换使用幂等键和唯一转换链路；重试不得重复建人、劳动关系或任职 |
| P2-REC-010 | `PENDING_ENTERPRISE_INPUT` | 招聘阶段、Offer正式字段、拒绝/撤回原因和可见范围等待企业招聘规则 |
| P2-REC-011 | `PENDING_ENTERPRISE_INPUT` | 候选人联系方式和Offer字段完成结构化、加密、脱敏、权限和保留规则前，只能使用合成数据 |

## 7. 人事事件与生效

### 7.1 事件类型

| 稳定代码 | 中文含义 | 当前通用结果 |
|---|---|---|
| `ONBOARDING` | 入职 | 待入职劳动关系转为有效 |
| `CONFIRMATION` | 转正 | 更新转正/试用结果 |
| `TRANSFER` | 调动 | 结束原主任职并建立目标主任职 |
| `CONCURRENT_ASSIGNMENT` | 兼岗 | 建立兼岗关系 |
| `SECONDMENT` | 借调 | 建立借调关系 |
| `END_ASSIGNMENT` | 结束任职 | 结束指定兼岗、借调或其他任职 |
| `TERMINATION` | 离职 | 劳动关系转为离职并结束相关结果 |
| `WITHDRAWAL` | 撤回入职 | 待入职劳动关系转为撤回 |
| `EMPLOYMENT_CORRECTION` | 人事更正 | 按白名单更正劳动关系字段 |
| `ROLLBACK_*` | 回退事件 | 形成新记录并恢复或补偿原结果 |

事件类型是稳定业务代码，企业流程名称变化不得改变代码含义。

### 7.2 通用规则

| 编号 | 状态 | 需求 |
|---|---|---|
| P2-EVT-001 | `CONFIRMED` | 同一事件可按场景直接生效或审批生效 |
| P2-EVT-002 | `CONFIRMED` | 审批通过的未来事件等待生效日期；到期处理不得重复执行 |
| P2-EVT-003 | `IMPLEMENTED_GENERIC` | 事件保存目标对象、事件类型、计划变更、执行方式、生效日期、原因、状态和幂等信息 |
| P2-EVT-004 | `IMPLEMENTED_GENERIC` | 执行前重新校验目标状态、有效日期、引用主数据和并发版本；失败不得部分写入 |
| P2-EVT-005 | `CONFIRMED` | 允许受控回退；回退保留原事件和审计，根据场景使用补偿事件、版本恢复或组合策略 |
| P2-EVT-006 | `CONFIRMED` | 回退支持直接生效和审批生效 |
| P2-EVT-007 | `CONFIRMED` | 下游已经同步时，回退或更正形成新记录，并以新记录重新同步 |
| P2-EVT-008 | `IMPLEMENTED_GENERIC` | 自动执行失败可使用同一幂等语义重试，不重复改变结果 |
| P2-EVT-009 | `PENDING_ENTERPRISE_INPUT` | 每种事件的输入字段、前置状态、审批节点、结果字段、释放规则和回退策略逐流程确认 |

### 7.3 入职已确认边界

- `ONBOARDING`只表示待入职劳动关系转为在职，不包含Offer确认和待入职建档。
- SSC可以发起；系统管理员可以代发起或补录，必须填写原因。
- HRBP、招聘人员、业务主管和员工本人本期不能发起。
- 只有`pending_start`劳动关系可以创建或执行入职事件。
- 同一劳动关系不能并行存在多个未结束的入职事件。
- 生效日期口径、审批节点、动态办理人和分支仍待确认。

## 8. 合同与协议

| 编号 | 状态 | 需求 |
|---|---|---|
| P2-CON-001 | `IMPLEMENTED_GENERIC` | 合同记录关联Person，并且最多关联一种劳动关系或协议关系 |
| P2-CON-002 | `IMPLEMENTED_GENERIC` | 保存合同类型、编号、主体、签署日、生效区间、提醒天数、版本和状态 |
| P2-CON-003 | `IMPLEMENTED_GENERIC` | 合同变更、续签、解除和取消使用显式动作，支持直接、审批和未来生效 |
| P2-CON-004 | `IMPLEMENTED_GENERIC` | 续签建立前后合同链；变更形成版本；动作具备幂等和回退 |
| P2-CON-005 | `IMPLEMENTED_GENERIC` | 到期提醒和状态刷新按查询/处理日期计算，不改写历史动作 |
| P2-CON-006 | `PENDING_ENTERPRISE_INPUT` | 合同/协议正式类型、字段、期限状态、编号规则和必填条件等待企业表头 |
| P2-CON-007 | `PENDING_ENTERPRISE_INPUT` | 附件格式、大小、存储、病毒扫描、保留、下载和明文访问权限待确认 |
| P2-CON-008 | `PENDING_ENTERPRISE_INPUT` | 电子签章、提醒渠道/对象、审批图和失败补偿待确认 |

开放的`metadata_payload`只用于通用工程验证，不允许把未建模的敏感字段或合同原文长期塞入JSON来规避字段评审。

## 9. 权限、审计与数据保护

- 首批操作角色为系统管理员和SSC。
- 账号、角色和启停由主管理员维护；停用账号永久撤销既有会话。
- 流程配置、流程办理、事件发起、事件执行、回退、合同操作和明文访问必须使用独立权限代码。
- 未知权限、未知办理人表达式和缺失兜底关系均默认拒绝。
- 审计至少记录操作者、代理/代办关系、时间、Trace ID、原因、业务对象、前后值摘要和来源。
- 密码、证件明文、合同原文及其他秘密不得进入审计日志。
- 候选人联系方式、人员证件和合同附件按敏感数据规则保护。
- 当前候选人`contact_payload`、应聘`offer_payload`和合同`metadata_payload`是通用JSON载荷，不具备企业敏感字段合同；不得写入真实联系方式、Offer薪资、证件、合同原文或秘密。

## 10. 异常与补偿

| 场景 | 处理原则 |
|---|---|
| 流程图无效或条件歧义 | 禁止发布或推进，返回可定位错误 |
| 动态办理人无法解析 | 不跳过审批，进入失败/人工补偿 |
| 审批期间业务对象已变化 | 执行时报告并发冲突，重新确认后再提交 |
| 生效日引用的组织/职务已失效 | 事件失败且不部分执行 |
| 自动任务中断 | 使用原幂等键安全重试 |
| 下游同步失败 | 本地已提交业务结果不回滚；记录失败并按事件重试 |
| 自动回退影响不明确 | 禁止自动处理，转人工评审 |

## 11. 非功能需求

- 所有业务写入使用数据库事务和迁移管理。
- 运行中流程和已生效事件不得物理删除。
- API必须提供稳定错误码、Trace ID和分页。
- 核心规则覆盖正常、边界、失败、并发、权限、幂等和回退测试。
- 后台到期任务可重复启动，且同一业务结果只应用一次。
- 第二阶段不以一万人同时提交流程作为完成条件；容量场景在非功能输入包中单独冻结。

## 12. 第二阶段完成定义

只有同时满足以下条件，第二阶段才能从“通用工程 MVP”升级为“企业业务验收通过”：

1. 入职、转正、调动、兼岗、借调、离职、撤回/更正流程逐项确认并发布。
2. 每个流程的发起人、节点、办理人、会签/或签、条件、超时和异常路径有明确版本。
3. Offer确认到待入职、入职到在职、未来生效和回退链路使用合成数据通过UAT。
4. 合同/协议正式字段、动作、附件和提醒边界确认并验收。
5. 普通办理人权限按任务和数据范围校验，不依赖主管理员通配权限。
6. 流程实例、任务、人事事件、结果、同步和审计可以对账。
7. 自动化测试、Docker复跑和业务Review报告通过。

## 13. 企业输入顺序

当前只按以下顺序处理，不要求一次补齐：

1. `P2-Q001`：入职生效日期来源、修改权限和审批晚于生效日的处理。
2. `P2-Q002`：入职审批节点、会签/或签和动态办理人。
3. `P2-Q003`：入职条件分支、驳回、撤回、超时和回退。
4. 依次处理转正、调动、兼岗、借调、离职、撤回/更正。
5. 合同/协议正式字段和附件规则。

模板和问题说明见[企业输入包06](../input-packs/06-hr-workflow-input.md)。

## 14. AI开发任务生成规则

- `CONFIRMED`条目可以形成企业业务任务和验收标准。
- `IMPLEMENTED_GENERIC`条目只能形成缺陷修复、确定性加固或与代码事实一致的UAT任务；不能自动升级为企业已完成。
- `PENDING_ENTERPRISE_INPUT`条目只允许生成资料模板、原型、合成测试脚手架或待确认问题，禁止固化字段、审批人、条件、时限和计算结果。
- 任一任务必须引用本文件需求编号、对应PRD页面和至少一个可重复验收场景。
- 收到用户新确认后，先更新项目决策和本规格状态，再生成MinimaxCode任务卡。
